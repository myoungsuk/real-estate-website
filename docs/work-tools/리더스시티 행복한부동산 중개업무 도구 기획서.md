## 1. 핵심 결론

이 도구는 **중개 업무에서 반복되는 계산·문구 작성·일정 관리·자료 정리를 운영자 휴대폰 한 곳에서 끝내기 위한 개인 업무 도구**다. 공개 홈페이지 기능이 아니며 고객은 이 화면을 보지 못한다.

다음 원칙으로 만든다.

1. 관리자 화면(`/admin/`) 아래에 둔다. 새 서버나 새 저장소를 만들지 않고 지금 쓰는 Cloudflare Worker 하나에 기능을 더한다.
2. 단계 0은 **아무것도 저장하지 않는 계산·문구 도구**로 시작한다. 지금 공개 화면에 있는 "비저장 문의 문장" 방식과 같아서 개인정보 위험이 가장 낮고 바로 쓸 수 있다.
3. 손님·계약 자료를 저장하는 단계 2부터는 **Git에 절대 넣지 않는다.** 같은 Worker에 Cloudflare D1(데이터)과 R2(비공개 파일)를 연결한다. 저장소는 코드만 있는 공개 상태로 둔다.
4. AI는 OpenAI 새 프로젝트를 Worker에서만 호출한다. 브라우저 직접 호출과 95번 서버 경유는 하지 않는다. 기본 모델은 `gpt-6.1-sol`이고, 계약서 두 번 읽기만 `gpt-6.1-sol`과 `gpt-6-astra`가 한 번씩 읽어 교차 확인한다. 추론 수준은 최고(`max`)다(2026-11-16 운영자 결정, 11.3절).
5. AI가 읽은 날짜·금액은 **사람이 확인한 뒤에만 저장**한다. AI 결과를 자동으로 저장하거나 공개하지 않는다. AI 정확도 합격 기준은 두지 않으므로 이 사람 확인 단계가 안전장치다(DEC-WT-11, 2026-11-17).
6. 모든 화면은 휴대폰(360px 폭)에서 먼저 쓰기 편하게 만든다.
7. 중개날개의 기능은 참고하되, 그 사이트의 문구·그림·로고·고유 이름·그림 파일은 복제하지 않는다. 관리자 화면 배치는 사용자가 승인한 시안(2026-11-16 15:05:43, 2026-11-18 17:55:44 CD1 선택으로 바뀜)을 따른다.

## 3. 배경

### 3.1 지금 일하는 방식의 문제

- 중개보수 계산, 가계약·약정금 안내 문자, 계약 일정 계산을 매번 손으로 한다. 요율 구간이나 한도액을 잘못 적용하거나 신고 기한을 하루 늦게 잡을 위험이 있다.
- 손님별 계약서·현장 사진·통화 녹음·메모가 휴대폰 사진첩, 메신저, 종이에 흩어져 있다. 1년 뒤 재계약이나 분쟁 때 필요한 자료를 찾는 데 시간이 든다.
- 계약일·중도금·잔금·거래신고·자금조달계획서 기한이 여러 곳에 적혀 있어 놓칠 수 있다.
- 지금 관리자 화면은 공개 콘텐츠만 다룬다. 관리자 저장이 공개 GitHub 저장소 커밋으로 이어지는 구조라서 손님 정보를 넣을 수 없다(`worker/github-content.mjs`, `src/lib/admin-resource-digest.mjs`의 `ADMIN_RESOURCE_PATHS` 허용 목록). 2026-11-16 `gh repo view`로 저장소가 공개 상태인 것을 확인했다.

### 3.2 중개날개 기능 분석

확인 출처(2026-11-19 보탬으로 고침):

- 2026-11-16: 중개날개 공개 홈페이지(`https://junggae-nalgae.kr/`) 본문을 확인했다. 같은 날 운영자 지시로 운영자의 체험 계정(빈 계정)을 읽기 전용으로 둘러봤고, 이어서 가상 데이터(가상 손님·가상 계약서·가상 등기부·가상 녹음, 실제 사람 정보 없음)로 계약서 인식·매물 글 초안·계약 문구·녹음 요약을 한 번씩 시험했다. 화면 기록은 저장소 밖 협업 보드에만 두고, 이 문서에는 기능 단위로 우리 말로만 적는다. 다른 서비스의 메뉴 이름·버튼 문구·화면 배치·고유 이름은 옮기지 않는다.
- 2026-11-18: 공개 화면 4개(첫 화면·이용약관·개인정보 처리방침·환불 안내)를 다시 확인했다. 그 사이트가 자동 수집을 허용한 주소(robots.txt)가 이 4개뿐이어서 근거도 이 4개로 한정한다.

공개 설명에 있는 보안·보관 약속: 매일 자동 백업과 30일 별도 보관, 전 구간 암호화 통신, 계정별 데이터 분리, 비공개 파일 저장, 구독 중단 뒤 자료 보관, 파일 내보내기.

주의할 점:

- 공개 설명의 "자금조달 신고기한 = 계약일 + 28일"은 법령 근거를 찾지 못했다. 법령상 기한은 거래신고 30일, 매수인이 중개사에게 자금조달계획서를 주는 기한 25일이다(보드 "A안 조사 결과", 날개-1 확인). 이 도구는 법령 기한을 쓴다. 2026-11-16 가상 계약서 시험에서도 인식 뒤 이 기한 일정이 계약일 + 28일로 생겼고, 거래신고 30일·자금조달계획서 25일 일정은 생기지 않았다. 2026-11-18 공개 화면의 예시 그림도 계약일 + 28일이었다(2026-11-19 보탬).
- 데이터가 국내에 있는지, 국외 이전 고지를 하는지, AI 처리 업체가 어디인지는 공개 설명만으로 확인하지 못했다. 2026-11-18 처리방침에는 운영·데이터베이스·파일 보관 위탁 업체와 AI 처리를 국내외 업체에 맡긴다는 내용이 있었지만, 저장 국가와 국외 이전 국가·시기·거부 방법은 없었다(2026-11-19 보탬).

### 3.3 직접 만드는 이유

1. **이미 있는 관리자 화면에 붙일 수 있다.** Cloudflare Access(허용 이메일 + 이메일 일회용 코드)와 JWT 재검증, Origin·CSRF 검증이 이미 동작한다(`worker/access-auth.mjs`, `worker/admin-security.mjs`). 로그인·권한 기능을 새로 만들 필요가 없다.
2. **사무소 매물·단지 정보와 한 화면에서 쓸 수 있다.** 공개 매물(`src/data/naver-listings.json`)과 단지 정보(`src/data/complexes.json`)를 문구 작성에 그대로 불러올 수 있다(단계 2 이후 후보).
3. **법령 기준을 우리가 정한다.** 위 "계약일 + 28일"처럼 외부 서비스의 기준을 그대로 믿지 않고, 법령 원문으로 확인한 기준과 하루 빠른 안전한 표시를 쓴다.
4. **자료를 우리 계정에 둔다.** 구독을 끊어도 자료가 남는지, 내보내기가 완전한지를 외부 업체에 의존하지 않는다.
5. **필요한 기능만 만든다.** 팀 공유·쪽지처럼 사무소 한 곳에서 두 계정이 같은 자료를 보는 구조에 필요 없는 기능은 만들지 않는다.

| ③ Access 애플리케이션 분리 | 업무 도구 경로를 별도 Access 앱으로 보호 | 채택하지 않음 |

이 결정에 따라 지켜야 할 것:

1. **작업 기록(감사 로그)을 남긴다.** 손님 자료를 보고(손님 카드·거래 열람, 목록·검색은 요청 1번에 1건, 파일 보기·내려받기), 만들고, 고치고, 지우고, 내보내고, AI를 부를 때(생성·취소·확정·음성 변환)마다 작업한 이메일, 시각, 동작 종류, 대상 ID를 D1에 기록한다. 보기까지 기록하는 이유는 "계정 하나가 넘어가 손님 자료가 열람되는 사고"를 감사 로그로 찾아낼 수 있어야 하기 때문이다(2026-11-16 대장 결정, 설계서 8.8절과 같음). 손님 이름·연락처·메모·검색어 같은 내용 원문은 감사 로그에 넣지 않는다. 이메일은 Worker가 검증한 Access JWT에서 읽고, 브라우저가 보낸 값을 믿지 않는다. 감사 기록을 쓰지 못하면 손님 자료를 돌려주지 않는다. 감사 로그는 사용자가 지우거나 고칠 수 없게 하고(수정·삭제 API 없음), 보존 기간은 3년이다(기간이 지나면 Cron이 자동 삭제. **확정**, DEC-WT-04, 2026-11-17 14:02:11 운영자 원문 "널널안 적용". 13:55:29에 설계서 제안값 1년으로 정했다가 14:02:11 널널안으로 바꿈).
2. **두 이메일 계정의 보안이 곧 손님 데이터 보안이다.** 로그인은 Cloudflare Access의 이메일 일회용 코드 방식이라서, 두 이메일 계정 중 하나라도 남에게 넘어가면 그 사람이 손님 자료 전체를 보고, 내보내고, 지울 수 있다. 그래서 다음을 운영 조건으로 둔다.
   - 두 이메일 계정 모두 2단계 인증을 켠다(운영자 계정 작업, 단계 2 운영 시작 전에 확인).
   - Access 세션 유지 시간을 지금보다 짧게 할지 설계서에서 정한다.
   - 감사 로그에서 평소와 다른 내보내기·대량 삭제·낯선 시각의 접근을 사용자가 확인할 수 있는 화면을 둔다.
   - 계정 분실·유출이 의심되면 ① Cloudflare Access 정책에서 그 이메일을 빼고 세션을 취소해 로그인을 막고 ② Worker의 허용 이메일 목록(`ADMIN_ALLOWED_EMAILS`)은 새 이메일로 바꿔 2개를 유지하는 절차를 운영 문서에 적는다. 허용 목록에서 1개만 빼면 `worker/access-auth.mjs`가 "정확히 2개" 검사에 걸려 콘텐츠 관리를 포함한 관리 API 전체가 503으로 멈춘다. 급하면 `WORK_TOOLS_ENABLED=false`로 업무 도구만 먼저 막는다.
3. **처리방침에 반영한다.** 손님 자료에 접근하는 계정이 2개라는 점을 처리 담당자 범위로 반영한다(10.6절).
4. **같은 자료를 두 계정이 동시에 고칠 수 있다.** 실시간 공유는 만들지 않지만, 저장할 때 다른 계정이 먼저 고친 내용을 덮어쓰지 않도록 기존 관리자 저장의 충돌 확인 방식(최신 버전 확인 후 저장)을 따른다(구현은 설계서).

## 6. 핵심 원칙

1. **데이터는 Git 밖에 둔다.** 손님·메모·일정·파일은 D1과 R2에만 저장한다. `src/data/`와 공개 저장소에는 넣지 않는다.
2. **필요한 것만 저장한다.** 주민등록번호, 신분증 사진, 계좌 비밀번호 같은 정보는 저장하지 않는다. 계약서 사진은 주민등록번호를 가린 사본만 다룬다(10.3절).
3. **사람이 확인한 뒤 저장한다.** AI가 읽은 값은 "제안"으로만 보여 주고, 사용자가 확인 버튼을 눌러야 저장한다.
4. **원문 위치를 보여 준다.** AI가 읽은 날짜·금액마다 사진의 어느 부분에서 읽었는지 표시해 사용자가 바로 대조할 수 있게 한다.
5. **로그에는 메타데이터만 남긴다.** 손님 이름·전화번호·메모·AI 입력과 응답 원문을 로그에 남기지 않는다(comibot 방식 참고).
6. **생성 요청은 자동 재시도하지 않는다.** 처리됐는지 모를 때 다시 보내면 비용이 두 번 든다. 실패하면 사용자에게 알리고 사용자가 다시 누른다.
7. **휴대폰에서 먼저 쓰기 편하게 만든다.** 한 열 화면, 큰 버튼, 짧은 입력 단계.
8. **예시는 가상 값만 쓴다.** 문서·테스트·화면 예시에 실제 손님 정보를 쓰지 않는다.

단계 P(2026-11-19 보탬. 두기·순서는 DEC-WT-18로 확정, 세부는 2026-11-19 v0.5 승인으로 확정)는 손님 자료를 다루지 않는 공개 자료 도구다(7.6절). 2026-11-16 13:26:09 운영자 결정(원문 "19 ~ 23 추천대로" 중 "실거래가 조회 넣음, 단계 1 후보, 공공데이터 API 키는 착수 승인 때")의 "단계 1 후보"를, 이 문서에서는 문서 승인 단계(단계 1)와 이름이 겹치지 않게 단계 P로 부른다. 2026-11-18 16:20:45 운영자 원문 "작업하는것 중에 실거래가 탭이랑 ai블로그 먼저 해줄 수 있어?"에 따라 단계 2 ~ 4를 기다리지 않고 따로 켜고 끌 수 있게 먼저 만든다. 순서는 실거래가 탭 → AI 블로그 글 초안이다(DEC-WT-18, 2026-11-19 07:25:18 운영자 질문 도구 답 "예, 실거래가 → AI 블로그 순 (Recommended)"). 손님 자료를 다루는 단계 2의 켜기 값(`WORK_TOOLS_ENABLED`)과 단계 4의 켜기 값(`WORK_AI_ENABLED`)을 켜지 않아도 동작해야 하므로 단계 P 전용 켜기 값을 따로 둔다(이름은 설계서에서 정함, 예: `WORK_REALPRICE_ENABLED`·`WORK_BLOG_ENABLED`).

### 7.1 단계 0 — 저장하지 않는 도구

공통 조건(**확정**):

- 입력값은 현재 페이지 메모리에서만 쓴다. 서버 요청, `localStorage`, URL에 넣지 않는다(공개 화면 "비저장 문의 문장"과 같은 원칙).
- 계산은 브라우저에서 한다. 서버 API를 새로 만들지 않는다.
- 금액은 원 단위 정수로 계산하고, 화면에는 천 단위 쉼표로 보여 준다.
- 법령 기준과 확인일을 화면 아래에 작게 표시한다.

#### 7.1.1 중개보수 계산기

사용자가 할 수 있는 일:

- 거래 종류(매매·교환 / 임대차), 대상(주택 / 오피스텔 / 그 밖의 건축물·토지)을 고르고 금액을 넣으면 법정 상한 중개보수를 바로 본다.
- 월세는 보증금과 월세를 넣으면 거래금액 환산(× 100, 합계 5천만 원 미만이면 × 70)을 자동으로 한다.
- 협의한 요율을 상한 이내에서 직접 넣어 실제 받을 금액을 본다.
- 부가세 10% 별도 표시를 켜거나 끈다.
- 결과를 문장으로 복사한다.

화면 흐름(모바일):

1. 거래 종류 선택(큰 버튼 2개)
2. 대상 선택(버튼 3개)
3. 금액 입력(매매가 / 보증금 / 보증금 + 월세). 숫자 키패드, 입력하면서 "1억 8,000만 원"처럼 한글 단위를 함께 표시
4. 결과 카드: 적용 구간, 상한 요율, 계산 금액, 한도액 적용 여부, 최종 상한 중개보수, 부가세 표시
5. 협의 요율 입력(선택): 상한보다 크면 입력을 막고 이유를 표시
6. "결과 복사" 버튼

입력·출력:

| 구분 | 항목 |
|---|---|
| 입력 | 거래 종류, 대상, 매매가 또는 보증금·월세, (오피스텔) 전용 85㎡ 이하와 부엌·화장실·목욕시설 여부, 협의 요율(선택), 부가세 표시 켜기·끄기 |
| 출력 | 거래금액(월세는 환산 과정 포함), 적용 구간, 상한 요율, 한도액, 상한 중개보수, 협의 요율 금액, 부가세 포함 금액(켰을 때), 법령 근거 문구 |

계산 기준(2026-11-16 국가법령정보센터 원문 대조 완료, 날개-1. 「공인중개사법 시행규칙」 [국토교통부령 제1611호] 제20조·별표 1·2. 세부 데이터 구조는 설계서 6.2절):

| 대상 | 구간 | 상한 요율 | 한도액 |
|---|---|---:|---:|
| 주택 매매·교환 | 5천만 원 미만 | 0.6% | 25만 원 |
| | 5천만 원 이상 ~ 2억 원 미만 | 0.5% | 80만 원 |
| | 2억 원 이상 ~ 9억 원 미만 | 0.4% | 없음 |
| | 9억 원 이상 ~ 12억 원 미만 | 0.5% | 없음 |
| | 12억 원 이상 ~ 15억 원 미만 | 0.6% | 없음 |
| | 15억 원 이상 | 0.7% | 없음 |
| 주택 임대차 | 5천만 원 미만 | 0.5% | 20만 원 |
| | 5천만 원 이상 ~ 1억 원 미만 | 0.4% | 30만 원 |
| | 1억 원 이상 ~ 6억 원 미만 | 0.3% | 없음 |
| | 6억 원 이상 ~ 12억 원 미만 | 0.4% | 없음 |
| | 12억 원 이상 ~ 15억 원 미만 | 0.5% | 없음 |
| | 15억 원 이상 | 0.6% | 없음 |
| 오피스텔(전용 85㎡ 이하 + 부엌·화장실·목욕시설) | 매매·교환 | 0.5% 이내 협의 | 없음 |
| | 임대차 | 0.4% 이내 협의 | 없음 |
| 그 밖의 건축물·토지(위 조건에 맞지 않는 오피스텔 포함) | 전체 | 0.9% 이내 협의 | 없음 |

- 대전은 「대전광역시 주택의 중개보수 등에 관한 조례」 제2조①에서 「공인중개사법 시행규칙」 별표 1 요율을 그대로 쓴다. 대전만의 요율표는 없다.
- 월세 거래금액: 보증금 + 월 차임 × 100. 이 합계가 5천만 원 미만이면 보증금 + 월 차임 × 70(시행규칙 제20조⑤).
- 검산 예시(가상 거래): 매매 1억 8,000만 원 → 90만 원이지만 한도 80만 원 적용 → 80만 원 / 매매 3억 원 → 120만 원 / 보증금 500만 원·월세 30만 원 → 500만 + 3,000만 = 3,500만 원(5천만 원 미만) → 500만 + 2,100만 = 2,600만 원 × 0.5% = 13만 원
- 부가세: 사무소가 일반과세자이므로 "부가세 10% 별도" 표시를 기본으로 켠다. 사용자가 거래마다 끌 수 있다(**확정**, DEC-WT-01, 운영자 원문 "1. 일반과세", 2026-11-16).
- 끝수: 원 미만은 버린다. 법령에 끝수 처리 규정이 없어 상한을 넘지 않는 쪽을 택한다(**확정**, DEC-WT-15, 운영자 원문 "5. 추천대로 해", 2026-11-16).

완료 기준:

- 테스트 체크리스트의 요율 경계(각 구간 경계 금액의 1원 아래·경계값), 한도액, 월세 × 100 / × 70 경계, 오피스텔 조건, 그 밖의 건축물, 부가세 켜기·끄기 시험을 모두 통과한다.
- 협의 요율이 상한을 넘으면 결과가 나오지 않는다.
- 결과 복사 문장에 법령 기준 확인일이 들어간다.
- 360px 폭에서 가로 넘침이 없다.

#### 7.1.2 가계약·약정금 안내 문자 생성

사용자가 할 수 있는 일:

- 계약 조건(물건 표시, 거래 종류, 금액, 가계약금, 입금 계좌 표시 방식, 계약 예정일, 특약 메모)을 넣으면 손님에게 보낼 안내 문자 초안을 만든다.
- 문체(정중한 기본형 / 짧은 형)를 고른다.
- 문장을 고친 뒤 복사해 문자·카카오톡 앱에서 직접 보낸다.

화면 흐름(모바일):

1. 문자 종류 선택: 가계약 안내 / 약정금 입금 안내 / 계약일 안내
2. 필요한 칸만 차례로 입력(한 화면에 3 ~ 5칸). 공개 매물에서 고르면 물건 표시·가격을 채워 넣는다(공개 정보만, 단계 0 선택 기능)
3. 미리보기: 빈 칸은 "[계약 예정일]"처럼 대괄호로 남겨 빠진 것을 바로 알 수 있게 한다
4. "복사" 버튼, "문자 앱 열기" 버튼(`sms:` 링크, 받는 사람 번호는 비워 둠)

입력·출력:

| 구분 | 항목 |
|---|---|
| 입력 | 문자 종류, 물건 표시(단지·동 공개 범위까지), 거래 종류, 거래 금액, 가계약금·약정금, 입금 기한, 계약 예정일, 특약 메모, 문체 |
| 출력 | 안내 문자 초안(편집 가능), 글자 수 |
| 넣지 않는 것 | 손님 이름·전화번호(문자 앱에서 사용자가 직접 고른다), 주민등록번호, 계좌 비밀번호 |

문구 원칙:

- 문구 틀은 우리가 새로 쓴다. 중개날개의 문구를 복제하지 않는다.
- 가계약금 반환 조건처럼 분쟁이 생기기 쉬운 내용은 사용자가 직접 확인하도록 "[반환 조건 확인]" 자리표시를 둔다. 도구가 법적 효력을 단정하는 문장을 넣지 않는다.
- 입금 계좌는 사용자가 입력한 값만 쓰고 저장하지 않는다.

완료 기준:

- 세 가지 문자 종류 모두 빈 칸 표시, 복사, 문자 앱 열기가 실제 Android Chrome·iPhone Safari에서 동작한다.
- 페이지를 새로 고치면 입력값이 남지 않는다(비저장 확인).
- 네트워크 요청 기록에 입력값이 나타나지 않는다.

#### 7.1.3 계약 일정 계산과 캘린더 파일

사용자가 할 수 있는 일:

- 계약일, 중도금일, 잔금일을 넣으면 거래신고 기한, (해당하면) 매수인의 자금조달계획서 전달 기한, 주택 임대차 신고 기한을 계산한다.
- 각 일정의 알림 시점(전날 저녁, 당일 아침 등)을 고른다.
- `.ics` 파일을 내려받아 휴대폰 캘린더에 한꺼번에 추가한다.

화면 흐름(모바일):

1. 거래 종류 선택: 매매 / 주택 임대차
2. 날짜 입력: 계약일(필수), 중도금일·잔금일(선택)
3. 해당 여부 선택: "자금조달계획서 제출 대상"(매매), "주택 임대차 신고 대상"(임대차, 금액·지역 조건 안내 포함)
4. 결과 목록: 날짜, 요일, 남은 일수, 근거 문구. 기한 항목은 "늦어도 이날까지"와 "법정 기한: 계약일부터 30일 이내"를 함께 표시
5. 알림 시점 선택
6. "캘린더에 추가(.ics)" 버튼

기한 계산 기준(**확정**, 보드 "중개업무 도구 확정 사항"):

| 일정 | 기준 | 화면 표시 |
|---|---|---|
| 부동산 거래신고 | 계약 체결일부터 30일 이내(부동산거래신고법 제3조①) | 계약일을 첫날로 세어 30일째 되는 더 이른 날짜를 "늦어도 이날까지"로 표시. 예: 가상 계약일 11/16 → 12/15 |
| 자금조달계획서 등 전달(법인·매수인 외의 사람이 신고하는 경우) | 25일 이내(시행규칙 제2조⑩: 법인 또는 매수인 외의 사람이 법인신고서등을 제출하는 경우 법인 또는 매수인이 신고하려는 사람에게 제공하고, 이 기간 안에 제공하지 않으면 법인 또는 매수인이 따로 제출. 2026-11-16 원문 확인) | 같은 방식. 예: 11/16 → 12/10 |
| 주택 임대차 신고 | 계약 체결일부터 30일 이내(부동산거래신고법 제6조의2) | 같은 방식. 대상: 보증금 6천만 원 초과 또는 월 차임 30만 원 초과, 보증금·차임 변동 없이 기간만 늘리는 갱신은 제외. 자치구가 포함되어 대전 동구는 대상 지역. 신고 의무자는 임대차계약 당사자 공동이고 중개사 의무는 없으며, 위임받으면 대행할 수 있다(시행령 제4조의3, 시행규칙 제6조의5, 2026-11-16 원문 확인) |
| 중도금·잔금 | 사용자가 입력한 날짜 | 그대로 표시 |

- 기간 계산은 해석에 따라 하루 차이가 날 수 있다(계약 11/16 → 12/15 또는 12/16). 놓치지 않도록 더 이른 날짜를 쓰고, 법정 기한 문구를 함께 적는다.
- 월말(예: 1/31 계약)과 윤년(2/29)을 포함한 날짜 계산은 테스트 체크리스트에서 시험한다.
- 기한 마지막 날이 주말이면 "(토요일)"·"(일요일)" 표시만 붙이고 날짜를 미루지 않는다. 공휴일은 v1에서 표시하지 않고 "공휴일 여부는 직접 확인하세요" 문구를 둔다. 대체공휴일·임시공휴일이 해마다 바뀌어 목록 관리 부담이 크기 때문이다(**확정**, DEC-WT-13, 운영자 원문 "3. 추천대로 해", 2026-11-16).

`.ics` 파일 조건:

- 표준 iCalendar 형식(RFC 5545). 일정마다 고유 ID, 하루 종일 일정, 알림(VALARM)을 넣는다.
- 일정 제목에 손님 이름을 넣지 않는다. 기본 제목은 "잔금(가상 단지 101동)"처럼 물건 표시만 쓰고, 사용자가 고칠 수 있게 한다.
- 파일은 브라우저에서 만들어 바로 내려받는다. 서버로 보내지 않는다.

완료 기준:

- 날짜 계산 시험(첫날 포함, 월말, 윤년, 25일·30일)을 모두 통과한다.
- 내려받은 `.ics`를 실제 iPhone 캘린더와 Android 캘린더 앱에 추가할 수 있다. Android는 캘린더 앱마다 `.ics`를 여는 방식이 달라 실기기 확인이 필수다(**추정**: 기본 캘린더 앱이 바로 열지 못하는 기기가 있을 수 있다).
- 알림이 선택한 시점에 울린다(실기기).

### 7.3 단계 2 — 손님·메모·일정·파일 보관

사용자가 할 수 있는 일:

| 기능 | 할 수 있는 일 |
|---|---|
| 손님 카드 | 손님을 등록하고 부르는 이름(예: "가상 손님 A"), 연락처, 찾는 조건(거래 종류·예산·지역·면적), 상태(상담 중 / 계약 진행 / 계약 완료 / 보류)를 적는다 |
| 메모 | 손님 카드에 날짜별 메모를 남긴다. 손님과 상관없는 메모는 "메모 창고"에 둔다 |
| 계약 일정 | 단계 0 일정 계산 결과를 손님 카드에 저장하고, 다가오는 일정 목록을 본다 |
| 파일 보관 | 계약서 사진(가린 사본), 현장 사진, 통화 녹음, 기타 문서를 손님 카드에 올린다 |
| 검색 | 손님 이름 일부, 연락처 뒷자리, 메모 단어, 상태로 찾는다 |
| 내보내기 | 손님 1명 또는 전체 자료를 파일(데이터 + 첨부 파일 묶음)로 내려받는다 |
| 삭제 | 손님 1명의 모든 자료(데이터 + R2 파일)를 지운다. 지우기 전에 이름을 다시 입력해 확인한다 |
| 정리 안내 | 손님 기록은 사용자가 직접 지울 때까지 보관한다(자동 삭제 없음). 기준일에서 1년이 지난 자료를 첫 화면에 "정리 안내 N건"으로 보여 주고, 사용자가 "지우기" 또는 "계속 보관"을 고른다(10.5절, DEC-WT-04) |
| 작업 기록(감사 로그) | 누가(허용 이메일 중 어느 계정) 언제 어떤 손님 자료를 보고, 만들고, 고치고, 지우고, 내보내고, 내려받고, AI로 보냈는지 본다. 내용 원문·검색어는 기록하지 않는다(5.3절) |

화면 흐름(모바일):

1. 업무 도구 첫 화면: 오늘·이번 주 일정, 최근 손님 5명, 검색창, "손님 추가" 버튼, (있을 때) "정리 안내 N건"
2. 손님 목록: 검색·상태 필터, 한 열 카드
3. 손님 카드: 기본 정보 → 일정 → 메모 → 파일 순서의 접이식 구역. 하단 고정 버튼(메모 추가, 사진 올리기)
4. 파일 올리기: 사진 선택 또는 촬영 → (계약서면) 주민등록번호 가리기 화면 → 올리기 진행 표시 → 완료
5. 내보내기·삭제: 손님 카드의 "더보기" 안에 둔다. 실수로 누르지 않게 첫 화면에 두지 않는다
6. 작업 기록: 설정 화면 안에 둔다. 최근 작업 목록(시각, 계정, 동작, 대상), 계정·동작별 필터

입력·출력:

| 구분 | 항목 |
|---|---|
| 입력 | 손님 기본 정보, 메모, 일정, 파일(사진·녹음·문서) |
| 출력 | 손님 목록·카드, 일정 목록, 검색 결과, 내보내기 파일 |
| 저장하지 않는 것 | 주민등록번호, 신분증 사진, 계좌 비밀번호, 가리지 않은 계약서 원본(10.3절) |

저장 위치(**확정**, 세부는 설계서·ADR-011):

- 데이터: Cloudflare D1(같은 Worker 바인딩)
- 파일: Cloudflare R2 비공개 버킷. 공개 주소(퍼블릭 버킷·r2.dev 주소)를 켜지 않고, 관리 API가 Access 검증 뒤에만 파일을 내려준다
- API: `/api/admin/v1/` 아래. 기존 Access JWT·허용 이메일·Origin·CSRF 검증을 그대로 쓴다

완료 기준:

- Access 없이, 또는 허용되지 않은 이메일로 업무 도구 API를 부르면 모두 거부된다.
- 허용 이메일 2개 계정 모두 같은 기능을 쓸 수 있고, 보기·목록·검색·파일 보기·내려받기·만들기·고치기·지우기·내보내기마다 감사 로그에 작업한 이메일·시각·동작·대상 ID가 남는다. 감사 로그에 손님 내용 원문·검색어가 없고, 감사 기록에 실패하면 자료가 돌아가지 않는다.
- 두 계정이 같은 손님 카드를 고쳐도 먼저 저장한 내용이 말없이 덮어써지지 않는다.
- R2 파일을 직접 주소로 열 수 없다.
- Git·빌드 산출물(`dist/`)·Worker 로그·deployment marker에 시험용 가상 손님 데이터가 0건이다.
- 삭제한 손님의 D1 행과 R2 파일이 실제로 사라진다. 백업에 남는 기간은 처리방침에 적는다(10.6절).
- 기준일에서 1년이 지난 가상 자료가 첫 화면 "정리 안내"에 나오고, 사용자가 "지우기"를 누르기 전에는 지워지지 않는다. "계속 보관"을 누르면 1년 뒤 다시 안내된다(10.5절).
- 내보내기 파일을 열면 등록한 데이터와 파일이 빠짐없이 있다.
- 백업·복원 훈련을 1회 이상 해서 복원된 데이터가 원본과 같다.
- 처리방침 수정안이 운영 시작 전에 준비되어 있다.

### 7.4 단계 3 — 알림, 얼굴 모자이크

#### 7.4.1 알림

사용자가 할 수 있는 일: 저장된 계약 일정을 휴대폰에서 알림으로 받는다.

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| ① 캘린더 구독 주소 | 일정을 iCalendar 구독 주소로 내보내 휴대폰 캘린더가 주기적으로 가져감 | 알림을 휴대폰 캘린더가 맡아 안정적. iPhone·Android 모두 지원 | 구독 주소는 Access 로그인 없이 열려야 해서 추측할 수 없는 긴 주소·취소 기능이 필요. 캘린더 앱이 가져가는 주기가 늦을 수 있음(추정, 수 시간) |
| ② 웹 알림(Web Push) | 브라우저 알림 권한을 받아 Worker가 알림을 보냄 | 아침·저녁처럼 원하는 시각에 보낼 수 있음 | iPhone은 홈 화면에 추가한 웹앱에서만 동작(**추정**, iOS 16.4 이상). 예약 발송을 위해 Cron Triggers가 필요 |
| ③ 단계 0 방식 유지 | 일정을 저장할 때마다 `.ics`를 내려받아 추가 | 가장 단순, 추가 위험 없음 | 일정이 바뀌면 다시 추가해야 하고 중복이 생길 수 있음 |

방식은 ① 휴대폰 캘린더 구독 주소로 정했다(**확정**, DEC-WT-05, 2026-11-17 13:55:29 운영자 원문 "A·B·C 적용, 결정 대기 추천대로", 14:02:11 "널널안 적용"에서도 그대로). 설계서에 있던 거래별 `.ics` 내려받기(③)도 그대로 둔다. 어느 방식이든 알림 문구에 손님 이름·연락처를 넣지 않는다.

완료 기준: 실기기(Android Chrome, iPhone Safari)에서 정해진 시각에 알림이 오고, 일정을 바꾸거나 지우면 알림도 바뀌거나 사라진다.

#### 7.4.2 얼굴 모자이크

사용자가 할 수 있는 일: 현장 사진을 밖으로 내보낼 때(블로그·문자 전송용 내려받기 등) 찍힌 사람 얼굴을 직접 가린 사본을 내려받는다.

- **앱 안에 보관하는 사진은 얼굴을 가리지 않는다.** 사진을 올릴 때 얼굴을 가리는 단계는 없다(EXIF·GPS 제거 등 기존 사진 처리는 그대로). 얼굴 가리기는 내보내기용이다(**확정**, DEC-WT-09, 2026-11-17 14:02:11 운영자 원문 "널널안 적용". 13:55:29에는 "수동 먼저"로 정했다가 바꿈).
- 처리는 브라우저에서 한다. 얼굴을 가리려고 사진을 외부 업체로 보내지 않고, 앱에 보관한 사진은 바꾸지 않은 채 가린 사본만 내려받는다(**확정**).
- **수동 모자이크만 만든다.** 사용자가 손가락으로 상자를 그어 얼굴을 가린다. 주민등록번호 가리기(10.3절)와 같은 화면을 재사용하므로 추가 라이브러리가 필요 없고 iPhone Safari·Android Chrome에서 똑같이 동작한다.
- **자동 얼굴 인식 라이브러리는 넣지 않는다(확정, DEC-WT-09).** 브라우저에서 얼굴 위치를 자동으로 찾으려면 얼굴 인식 모델을 담은 브라우저 라이브러리가 필요하다. Chrome의 실험 기능(Shape Detection API)은 iPhone Safari에서 쓸 수 없는 것으로 알고 있다(**추정**). 운영자가 승인한 "Worker(JavaScript) + 직접 fetch"는 Worker에서 OpenAI를 부를 때 SDK를 쓰지 않는다는 결정이고, 브라우저 라이브러리는 DEC-WT-09로 따로 정했다.
- **AI로 얼굴 위치를 찾는 방식은 추천하지 않는다.** 원본 사진을 OpenAI로 보내야 해서 국외 이전 항목(10.2절)이 늘어나고, "얼굴은 브라우저에서 처리한다"는 원칙과도 맞지 않는다.

완료 기준: 내려받은 가린 사본의 EXIF·GPS 정보가 지워지고, 가린 부분을 되돌릴 수 없다(원본 픽셀이 남지 않음). 앱에 보관한 사진은 바뀌지 않는다.

### 7.5 단계 4 — AI

공통 조건(**확정**, 보드 "중개업무 도구 확정 사항"과 "comibot 조사 결과"):

- OpenAI 새 프로젝트를 만들고 comibot과 키를 나눈다. 키는 Cloudflare Secret에만 둔다. 키는 운영자가 Cloudflare 대시보드의 Worker Secret에 직접 입력한다(DEC-WT-06 중 키 전달 방법만 확정, 2026-11-17). 새 프로젝트·키·월 예산 상한 만들기는 단계 4 착수 전 할 일로 남는다(결정 대기 6).
- 기본 모델은 `gpt-6.1-sol`(모든 작업), 계약서 두 번 읽기만 1회 `gpt-6.1-sol` + 1회 `gpt-6-astra` 교차, 추론 수준은 최고(`max`)다(2026-11-16 운영자 원문 "아니대 18번 추천대로하자"). 처음 결정 "비용과 상관없이 최상위 모델"에서 바뀐 경위는 11.3절. 모델 이름은 작업별 설정값으로 두고, 단계 4 시작 때 가상 계약서 표본으로 재어 확정한다.
- `store:false`, 생성 요청 재시도 0회, 로그는 메타데이터만, 반복 호출을 막는 높은 예산 상한을 둔다.
- 날짜·금액 추출은 JSON 스키마 + 원문 위치 + 두 번 읽어 비교 + 사람 확인 뒤 저장.
- 최고 추론 수준은 응답이 수십 초 이상 걸릴 수 있다(**추정**). 화면은 진행 상태를 보여 주고, 휴대폰 화면이 꺼지거나 연결이 끊겨도 결과를 다시 받을 수 있어야 한다(방식은 설계서).

#### 7.5.1 계약서 사진 인식 → 일정 자동 등록

1. 사용자가 계약서를 촬영하거나 사진을 고른다(여러 장 가능).
2. 브라우저에서 문서 영역 자르기·기울기 보정을 한다.
3. 사용자가 주민등록번호 위치에 상자를 그어 가린다. 가리기 전에는 다음 단계로 갈 수 없다.
4. 가린 사진을 고해상도로 올린다.
5. Worker가 OpenAI에 같은 사진을 두 번 독립적으로 읽게 한다. 결과는 JSON 스키마(계약일, 중도금일·금액, 잔금일·금액, 거래 금액, 물건 표시 등 + 원문 위치)로 받는다.
6. 두 결과가 다른 칸은 노란색 + "다시 확인" 문구로 표시한다(색만으로 구분하지 않는다).
7. 사용자가 사진 옆에서 값을 확인·수정한 뒤 "확인하고 저장"을 누르면 손님 카드의 일정으로 저장되고 7.1.3의 기한이 계산된다.

완료 기준: 정확도 합격 기준은 두지 않는다(DEC-WT-11, 2026-11-17). AI 결과는 항상 사람이 확인한 뒤 저장하고(계약서 숫자는 틀리면 사고라 사람 확인 단계는 남긴다), 확인 전 저장 경로가 0개다. 가상 계약서 표본 세트(실제 손님 계약서는 쓰지 않음)로 재는 날짜·금액 정확도는 DEC-WT-17 모델 비교("Sol 두 번" 대 "교차")에만 쓴다.

#### 7.5.2 등기부 → 약정금 안내 문자

1. 등기사항증명서 PDF 또는 사진을 올린다.
2. AI가 소유자 표시(가린 상태), 근저당 등 권리 관계 요약, 물건 표시를 읽어 제안한다.
3. 사용자가 확인하면 7.1.2 문자 생성기의 "예금주 대조" 안내와 "확인할 권리 관계" 줄에만 값이 채워진다.
4. 중개보수 계산기(7.1.1)에는 값을 자동으로 채우지 않는다. 등기부 갑구에 적힌 거래가액은 과거 소유권 이전 때의 가격이지 이번 거래 금액이 아니기 때문이다(2026-11-16 날개-1 검토, 설계서 14.7절과 같음).

주의: 등기부에는 소유자 성명·주소 등 개인정보가 들어 있다. 주민등록번호 뒷자리 가리기(10.3절) 기준을 똑같이 적용한다. 소유자 이름은 문자 초안에만 쓰고 저장하지 않는다. 권리 분석의 최종 판단은 사람이 한다.

#### 7.5.3 상담 녹음 → 글자 → 요약

녹음을 받는 길은 두 가지다. 웹 페이지는 휴대폰 전화 통화를 녹음할 수 없으므로 통화는 ①, 사무실·현장의 대면 상담은 ②를 쓴다.

| 구분 | ① 통화 녹음 파일 올리기 | ② 화면 안 녹음(대면 상담) |
|---|---|---|
| 쓰는 때 | 전화 상담 | 사무실·현장에서 마주 앉은 상담 |
| 녹음 주체 | 휴대폰 기본 통화 녹음 기능(운영자 휴대폰) | 업무 도구의 녹음 화면 `/admin/work/record/`(브라우저 마이크, 설계서 14.11절) |
| 결정 | 기존 설계 | **확정**(DEC-WT-14, 운영자 원문 "4. 어 녹음하게 해", 2026-11-16. 설계서 추천은 "허용하지 않음"이었으나 운영자가 허용으로 정함) |
| 길이 처리 | 25MB 이하 파일은 그대로 올린다. 25MB를 넘는 파일은 PC에서만 브라우저가 나눠 올리고(휴대폰은 메모리 부족 위험, 48kHz 스테레오 1시간을 풀면 약 1.4GB, 추정), 휴대폰에서는 "녹음 앱에서 나눠 저장해 주세요"를 안내한다 | 녹음하는 동안 3분마다 녹음을 멈췄다 바로 다시 시작해 단독으로 변환되는 조각 파일(약 1.5MB)을 만들고, 조각이 끝나는 즉시 올린다. 그래서 휴대폰에서도 긴 상담을 녹음할 수 있다. 한 묶음은 최대 120분(조각 40개, 설계서 제안값) |

공통 흐름:

1. (② 전용) 녹음을 시작할 때 "손님께 안내하셨나요?" 안내를 한 번 띄운다. 안내에는 손님에게 알릴 내용(녹음 사실, 녹음 원본을 기본 1년 보관한다는 점, 글자 변환·요약을 위해 국외(미국) 업체로 전송된다는 점)을 보여 준다. 확인을 누르지 않아도 녹음된다(**확정**, DEC-WT-16, 2026-11-17 14:02:11 운영자 원문 "널널안 적용". 13:55:29에는 "법률 확인 전까지 '손님에게 안내함'을 눌러야 녹음이 켜짐"으로 정했다가 바꿈). 대화 당사자 녹음은 합법이라는 판단은 대장 판단이고 변호사 확인은 아니다.
2. 녹음 파일 또는 조각을 R2에 올린다. 올린 녹음 원본은 기본 1년 보관한다(5번).
3. 변환 전 "상대방 개인정보가 국외 AI 업체로 전송됩니다" 확인 단계를 거친다.
4. 변환은 휴대폰 연결과 떼어 놓는다. 브라우저는 변환 "작업"만 등록하고, 매분 도는 Cron이 대기 작업을 여러 개 가져가 몇 개씩 동시에 OpenAI 음성 → 글자 변환을 부른다(처리 개수·용량 한도는 설계서 14.6절, 2026-11-16 공식 문서 기준 권장 모델 `gpt-transcribe`, 파일 25MB 한도, 구현 시점 재확인). 그래서 화면이 꺼지거나 창을 닫아도 변환은 계속되고, 브라우저는 진행 상태만 본다. 결과는 기본 모델(`gpt-6.1-sol`, 최고 추론)로 요약한다(손님 요구 조건, 예산, 일정, 약속한 일, 다음 할 일). comibot에는 참고할 음성 변환 코드가 없어 새로 설계한다(설계서 14.6절).
5. 녹음 원본(통화 녹음 파일·대면 녹음 조각)은 글자 결과를 메모로 저장한 뒤에도 지우지 않고 기본 1년 보관한다. 사용자가 언제든 직접 지울 수 있고, 올린 날에서 1년이 지나면 정리 안내에 나온다(자동 삭제 아님. **확정**, DEC-WT-10, 2026-11-17 14:02:11 운영자 원문 "널널안 적용". 13:55:29에는 "기본 보관 안 함(메모 저장 뒤 삭제), 고른 경우만 30일"로 정했다가 바꿈). 변환이 실패하거나 결과를 모르는 상태(`unknown`)가 되어도 원본이 남아 있으므로 다시 실행할 수 있다. 올리다 끊겨 완성되지 않은 업로드 조각을 치우는 48시간 정리는 녹음 보관이 아니라 기술 정리다(**설계 선택**, 대상은 설계서 8.7·14.6절). 대면 녹음 묶음에서 일부 조각만 실패하면 "실패한 조각만 다시"(그 조각만큼만 새 비용) 또는 "빠진 채로 끝내기"(메모에 빠진 조각 표시)를 고른다(설계서 14.11절).
6. 사용자가 요약을 확인·수정한 뒤 손님 메모로 저장한다. 요약 안의 일정 후보는 사람이 확인한 뒤에만 일정이 된다.

화면 안 녹음(②)의 추가 조건:

- 마이크 권한은 녹음 화면 경로에서만 허용한다. 지금 전역 보안 헤더는 `Permissions-Policy: microphone=()`라서 모든 화면에서 마이크가 막혀 있다. 녹음 화면 경로에만 전역 값을 떼고(`! Permissions-Policy`) 마이크를 허용한 값을 다시 적는 방식으로 바꾼다. 같은 헤더를 그냥 덧붙이면 Cloudflare가 두 값을 합쳐 결과를 장담할 수 없기 때문이다. 공개 화면과 다른 관리자 화면은 `microphone=()`를 그대로 둔다.
- `public/_headers` 변경은 보안 헤더를 일부 완화하는 일이므로 운영자의 별도 승인을 받는다(🔒). 바꾼 뒤 각 경로 응답에 `Permissions-Policy`·`Content-Security-Policy`가 하나씩만 있는지 시험한다.
- 화면이 꺼지거나 다른 앱으로 넘어가면 브라우저가 녹음을 멈출 수 있다(특히 iPhone Safari, **추정**). 녹음 중에는 화면 꺼짐 방지를 요청하고, 화면이 숨겨지면 진행 중 조각을 바로 올린 뒤 돌아왔을 때 경고와 "이어서 녹음"을 보여 준다. 창을 닫아도 이미 올린 조각은 남고, 업무 도구 첫 화면에 "끝나지 않은 녹음"으로 알린다.
- 연결이 끊기면 녹음은 계속하고 조각을 잠시 메모리에 쌓았다가 다시 올린다. 쌓인 조각이 5개(약 15분)를 넘으면 녹음을 멈춘다. 휴대폰 저장소에는 녹음을 저장하지 않는다(기기에 손님 음성이 남지 않게).
- 녹음 형식은 브라우저가 지원하는 것을 `audio/mp4` → `audio/webm;codecs=opus` → `audio/ogg;codecs=opus` 순서로 고른다(iPhone Safari는 MP4, Android Chrome은 WebM이 일반적, **추정**, 실기기 확인). 세 형식 모두 서버 허용 형식과 변환 API 지원 형식에 들어 있다.
- 녹음한 소리를 화면에서 다시 듣는 기능은 v1에 두지 않는다(보안 헤더 `media-src` 변경을 피하기 위해).

주의: 통화·대면 상대방의 개인정보가 OpenAI(국외)로 간다. 10.2·10.4절 조건을 먼저 충족한다.

#### 7.5.4 사진·메모 글자 검색

- 사진을 올릴 때(사용자가 고른 경우) AI가 사진 속 글자를 읽어 D1 검색 색인에 넣는다.
- 검색창에서 사진 속 글자와 메모를 함께 찾는다.
- 이미 올린 사진의 글자 읽기는 사용자가 범위를 골라 실행한다(비용 통제).

#### 7.5.5 사진 제목 일괄

- 여러 장을 고르면 AI가 "거실 남향 창", "욕실 리모델링 전"처럼 짧은 제목을 제안하고, 사용자가 확인한 뒤 한꺼번에 적용한다.

단계 4 공통 완료 기준:

- 로그·D1 일반 행에 AI 입력·응답 원문이 남지 않는다(사용자가 저장한 결과만 남음).
- 생성 요청 자동 재시도가 0회다.
- 예산 상한에 걸리면 호출이 멈추고 화면에 이유가 표시된다.
- 긴 대기와 연결 끊김 뒤에도 결과를 다시 받거나 실패를 분명히 알린다.
- 주민등록번호를 가리지 않은 사진은 올릴 수 없다.

### 7.6 단계 P — 공개 자료 도구 (2026-11-19 보탬)

공통 조건:

- 손님 자료(이름·연락처·메모·계약)를 받지도, 저장하지도 않는다. 공개 자료와 사무소 확정 공개 정보만 쓴다.
- 결과는 관리자 화면에서만 보인다. 공개 홈페이지·sitemap·`llms.txt`·공개 JSON(`src/data/`)·빌드 산출물(`dist/`)에 실거래 자료와 글 초안을 넣지 않는다. 지금 공개 단지 상세의 FAQ가 "단지정보에 현재 시세를 고정하지 않는 이유"를 "최신 가격은 게시일과 확인일이 있는 공개 매물과 콘텐츠에서 별도로 확인"한다고 안내하고 있으므로(`src/data/complexes.json`), 공개 화면에 시세를 보이는 일은 이 문서 범위가 아니다. 나중에 공개 화면에 보이려면 그 FAQ 문구와 함께 따로 정한다. 홍보물에 자료 기준 시각을 늘 붙이는 것은 이 FAQ 안내와도 맞는다.
- 홍보물과 글은 사람이 읽고 복사하거나 내려받아 직접 올린다. 자동 게시는 하지 않는다(01 기획서 비목표 "AI 생성 내용의 자동 공개" 유지).
- API는 `/api/admin/v1/work/` 아래에 두고 기존 Access JWT·허용 이메일·Origin·CSRF 검증을 그대로 쓴다. 켜기 값은 단계 P 전용으로 따로 둔다(7.0절, DEC-WT-18).
- 외부 인증키(공공데이터포털)와 OpenAI 키는 운영자가 Cloudflare 대시보드의 Worker Secret에 직접 입력한다. 키를 대화·협업 보드·저장소·로그에 적지 않는다(DEC-WT-06과 같은 방식).
- 글 초안 만들기 요청은 감사 로그의 AI 호출 기록 규칙(작업한 이메일·시각·동작, 내용 원문 없음, 5.3절)을 따른다. 공개 실거래 자료 보기는 손님 자료가 아니므로 감사 로그 대상에서 뺀다(설계서에서 확정).

#### 7.6.1 실거래가 탭

자료: 국토교통부가 공공데이터포털에 제공하는 아파트 실거래가 공개 API 4개(DEC-WT-19, 2026-11-19 확정). 대전 동구(시군구 코드 `30110`) 한 곳만 받는다. 국토교통부 실거래가 공개시스템의 웹 화면은 긁어 오지 않는다(10.8절).

| 운영자가 신청할 API(공공데이터포털 이름 그대로) | 자료 번호 | 쓰는 곳 |
|---|---|---|
| 국토교통부_아파트 매매 실거래가 상세 자료 | 15126468 | 매매 거래 목록·신고가(기본) |
| 국토교통부_아파트 매매 실거래가 자료 | 15126469 | 상세 자료와 비교·대체용 |
| 국토교통부_아파트 전월세 실거래가 자료 | 15126474 | 전세·월세 거래 목록 |
| 국토교통부_아파트 분양권전매 실거래가 자료 | 15126471 | 분양권 거래 목록 |

네 API 모두 무료이고 개발·운영 계정 모두 자동 승인이며, 개발 계정 하루 호출 한도는 10,000건, 이용허락범위는 "제한 없음"이다(2026-11-19 공공데이터포털 자료 화면 확인). 인증키는 공공데이터포털 계정에 하나 나오고 승인된 API에 함께 쓰는 것으로 본다(**추정**, 발급 화면에서 확인). 공개 범위는 매매가 층과 등기를 마친 거래의 동, 전월세와 분양권이 층까지이고, 호수는 어느 자료에도 없다.

사용자가 할 수 있는 일:

| 기능 | 할 수 있는 일 |
|---|---|
| 새 거래 | 최근 들어온 거래를 계약일 순으로 본다(매매·전세·월세·분양권) |
| 관심 단지 | 기본으로 리더스시티 4·5블록과 신흥 SK뷰를 두고, 동구 안의 다른 단지를 더하거나 뺀다. 단지는 국토교통부 자료의 단지 고유번호(`aptSeq`) 기준으로 고르고, 우리 `complexes.json` 단지와의 연결은 설계서에서 정한다 |
| 신고가 표시 | 신고가 기준(DEC-WT-21)을 넘은 거래에 글자로 "신고가"를 붙인다(색만으로 구분하지 않음) |
| 거르기 | 기간, 전용면적, 금액, 거래 종류, 법정동, 해제된 거래 빼기(기본 켬), 직거래 빼기, 분양권 보기 |
| 갱신 시각 | 마지막으로 자료를 받은 시각과 받은 범위(몇 월분까지)를 화면 위에 보인다. 받기에 실패하면 실패 이유(하루 한도 초과·인증키 만료 등)를 보인다 |
| 홍보물 만들기 | 고른 거래 몇 건으로 글과 그림을 만든다(아래) |

자료 받기(방식은 설계서 22장):

- Worker의 Cron이 하루 몇 번(예: 4번) 자료를 받는다. 실거래는 계약일부터 30일 안에 신고하고 해제도 해제가 확정된 날부터 30일 안에 신고하므로(**추가 확인 필요**: 법령 원문 대조), 매번 이번 달과 직전 3개월을 다시 받아 늘어난 거래와 해제 표시를 반영한다. 해제가 늦게 붙는 경우를 위해 그보다 오래된 달(예: 최근 12개월)도 더 긴 주기로 다시 받는다(주기는 설계서).
- 처음 한 번은 과거 자료를 채운다. 매매는 2006년 1월, 분양권은 2007년 6월 29일 이후 계약분, 전월세는 2021년 6월부터 공개된다(국토교통부 실거래가 공개시스템 안내). 신고가 판정에 과거 자료가 필요하기 때문이다. 시군구 1곳 × 1개월이 호출 1번이므로 처음 채우기는 수백 번, 그 뒤 하루 받기는 100번 안팎이라 하루 한도 10,000건보다 훨씬 적다(**추정**).
- Workers 무료 플랜은 실행 1번에 보낼 수 있는 외부 요청 수가 적어 나눠 받아야 할 수 있다(**추정**). 나눠 받기와 이어 받기는 설계서에서 정하고, Workers Paid 전환 시점(DEC-WT-12)과 함께 판단한다.
- 받은 자료는 D1의 공개 실거래 자료 표에 둔다(DEC-WT-20, 2026-11-19 확정). 손님 자료 표와 연결하지 않는다. 지금 ADR-011은 D1에 손님·메모·거래·일정·감사 로그만 둔다고 적고 있어, 공개 자료 표를 두려면 ADR-011 보탬이 먼저 필요하다(4.3절).
- Cron 설정(`wrangler.jsonc`)과 Secret 이름 추가는 배포 설정 변경이므로 별도 승인(🔒)을 받는다.
- 인증키는 요청 주소(쿼리 문자열)에 들어가므로 요청 주소 전체를 로그·오류 메시지·화면에 남기지 않는다. 개발 계정 활용 기간이 끝나면 키가 막히므로(**추가 확인 필요**: 기간) 만료 오류를 화면에 보인다.

홍보물:

- 글 4가지(스레드·인스타그램·블로그·카카오톡용)는 AI 없이 문구 틀로 만든다. 숫자는 받은 자료 그대로 쓰고 계산 함수가 만든다.
- 카드 그림은 브라우저 `canvas`로 PNG를 만들어 내려받는다. A4 한 장은 인쇄용 화면으로 만들고, PDF는 브라우저의 "PDF로 저장"을 쓴다. 그림 틀과 문구는 새로 만든다(RISK-16).
- 홍보물에는 다음을 자동으로 붙인다: 자료 출처("국토교통부 실거래가 공개 자료, 공공데이터포털"), 자료를 받은 시각, "계약일 기준이며 신고 기한(30일) 때문에 최근 거래는 늘어날 수 있음, 해제된 거래 제외" 안내, 사무소 명시사항(명칭·소재지·연락처·등록번호·대표 성명, 10.9절).
- 홍보물에는 동 번호를 빼고 층은 숫자 그대로 쓴다(DEC-WT-22, 2026-11-19 확정).
- 손님에게 보내는 공개 링크는 만들지 않는다. 그림·글·PDF를 내려받아 운영자가 직접 보낸다(공유 링크를 넣지 않는 DEC-WT-03과 같은 이유).

완료 기준:

- 공개 홈페이지·sitemap·`llms.txt`·`dist/`·공개 JSON에 실거래 자료가 0건이다.
- 인증키가 저장소·로그·화면·오류 메시지에 0건이다.
- 해제된 거래를 빼면 목록과 신고가 판정에서 모두 빠진다. 다시 받은 달의 거래가 두 번 들어가지 않는다.
- 하루 한도 초과·인증키 만료·응답 오류 때 앞서 받은 자료를 지우지 않고 실패 이유를 보인다.
- 홍보물에 출처·기준 시각·안내 문구·사무소 명시사항이 빠짐없이 붙는다.
- 360px 화면에서 가로 넘침이 없고 주요 버튼이 44×44px 이상이다.

#### 7.6.2 AI 블로그 글 초안(SNS 짧은 광고 문구 포함)

사용자가 할 수 있는 일: 공개 매물 1건 또는 공개 단지 1곳을 골라 네이버 블로그용 글 초안과 SNS용 짧은 광고 문구를 받고, 광고 명시사항이 붙은 글을 확인한 뒤 복사해 직접 올린다.

입력:

| 구분 | 내용 |
|---|---|
| 고를 수 있는 자료 | 지금 공개 중인 매물(`naver-listings.json`에 있는 매물, `listings.json`의 `published` 매물)과 공개 단지(`complexes.json`), 사무소 확정 공개 정보(`office.json`). 목록에서 빠진(등록 종료된) 매물과 초안 매물은 고를 수 없다(이미 계약된 줄 알면서 하는 광고는 부당 광고 유형, 10.9절) |
| 화면에서만 받는 값 | 명시사항 중 공개 자료에 없는 항목(예: 방·욕실 개수, 입주 가능일, 관리비, 총 층수, 사용승인일, 주차 대수)과 글 유형·강조점. 명시사항 칸 값은 초안 기록 안에 함께 두고 초안과 함께 지운다(확정·취소 뒤 30일, DEC-WT-33, 2026-11-19 09:13:09 확정). 다시 열어도 복사할 수 있다. 글 유형·강조점은 저장하지 않고 이번 요청에만 쓴다 |
| 받지 않는 값 | 손님·소유자·임차인 정보, 공개 광고에 없는 호수, 중개보조원 정보 |
| 자유 입력 칸 검사 | 주민등록번호 형식, 사무소 번호가 아닌 전화번호 형식이 있으면 보내기 전에 막는다 |

처리:

1. Worker가 OpenAI를 부른다. 모델과 추론 수준은 단계 4와 같은 규칙(기본 `gpt-6.1-sol`, 최고 추론, 작업별 설정값, `store:false`, 생성 요청 재시도 0회, 하루 한도·월 예산 상한 공유)을 따른다(7.5절 공통 조건, DEC-WT-17). 단계 P가 단계 4보다 먼저 오므로 이 공통 조건을 단계 P에서 먼저 만든다.
2. 결과는 JSON(제목, 단락, 해시태그, 글에 쓴 사실 목록)으로 받는다.
3. Worker가 결과를 검사해 화면에 보인다.
   - 글 속 숫자(가격·면적·층·날짜)가 입력과 같은지 대조한다. 다르면 복사를 막는다.
   - 입력에 없는 시설·거리·학군·교통·생활 편의 주장을 찾아 경고한다. 2026-11-16 시험에서 다른 서비스의 글 초안이 확인되지 않은 생활 편의 문장을 지어냈다(3.2절).
   - "직선거리" 같은 거리 표현을 경고한다(교통시설 거리를 도보가 아닌 직선거리로 쓰는 것은 부당 광고 유형, 10.9절).
   - 지어낸 손님 후기와 가상 인물은 만들지 않는다.
4. 광고 명시사항 블록은 AI가 아니라 코드가 붙인다. 사무소 5항목(명칭·소재지·연락처·등록번호·대표 성명)은 `office.json` 확정 공개 정보로 채우고, 매물 항목(소재지·면적·가격·종류·거래 형태·총 층수·사용승인일·방향·방 개수·욕실 개수·입주 가능일·주차 대수·관리비)은 공개 자료와 화면 입력값으로 채운다. 층은 저·중·고로 바꿔 쓸 수 있고, 호수는 넣지 않는다. SNS 짧은 문구에도 같은 블록을 붙인다.
5. 법이 요구하는 명시사항이 하나라도 비면 복사 버튼을 막는다(DEC-WT-23, 2026-11-19 확정).
6. 사용자가 읽고 고친 뒤 복사한다. 자동 게시하지 않는다.

비용(**추정**, 11.3절): 글 1편에 입력 약 4,000토큰, 출력 상한 20,000토큰이면 최대 약 0.21달러, 평균 출력 5,000토큰이면 약 0.06달러다. 월 30편이면 약 1.7 ~ 6.2달러다.

초안 보관은 따로 보관함을 만들지 않고 AI 작업 기록 규칙(확정·취소 뒤 30일 자동 삭제)을 그대로 쓴다(DEC-WT-24, 2026-11-19 확정).

완료 기준:

- 목록에서 빠진 매물과 초안 매물을 고를 수 없다.
- 글 속 가격·면적·층·날짜가 입력과 다르면 복사할 수 없다.
- 명시사항 블록이 항상 붙고, 중개보조원 정보와 호수가 0건이다.
- OpenAI로 보내는 요청에 손님 정보 형식(주민등록번호·사무소 밖 전화번호)이 0건이다.
- 예산 상한·하루 한도에 걸리면 호출이 멈추고 이유가 보인다. 생성 요청 자동 재시도가 0회다.

### 7.7 추가 후보 기능의 단계 배치 (2026-11-19 보탬)

### 10.2 국외 이전 (Cloudflare·OpenAI)

- Cloudflare D1의 위치 힌트(`apac` 등)는 "가까운 곳" 선호일 뿐 보장이 아니고, 한국을 지정하는 관할(jurisdiction) 선택지는 없다(2026-11-16 공식 문서 확인, 설계서 8.10절). R2도 같은 방식으로 본다. 따라서 손님 데이터가 국외에 저장된다고 보고 대응한다.
- OpenAI는 미국 업체다. 단계 4에서 보내는 사진·녹음·글은 국외로 이전된다. 특히 대면·통화 녹음을 OpenAI(미국)로 보내 받아쓰기하는 것은 개인정보 국외 이전이므로 처리방침에 적는다(**확정**, DEC-WT-16, 2026-11-17, 단계 4 처리방침 수정 때, 10.6절).
- 개인정보 보호법의 국외 이전 조항(제28조의8)에 따라 이전받는 자, 이전 국가, 이전 항목, 이전 시기·방법, 보유기간, 거부 방법 등을 처리방침에 공개하거나 정보주체에게 알려야 하는지 확인해야 한다(**추가 확인 필요**). 손님과의 중개계약 이행에 필요한 처리위탁·보관인지, 별도 동의가 필요한지에 따라 화면·문구가 달라진다. 지금 결정(DEC-WT-16)은 대면 녹음에 별도 동의 확인을 받지 않고 처리방침에 적는 것이며, 이 법 해석은 대장 판단이고 변호사 확인은 아니다.
- 단계 2 운영 시작 전에 Cloudflare 항목을, 단계 4 운영 시작 전에 OpenAI 항목을 처리방침에 반영한다.
- 단계 P의 AI 블로그 글 초안은 공개 매물·단지·사무소 정보만 OpenAI로 보낸다. 손님 개인정보가 국외로 가지 않도록 자유 입력 칸에 손님 정보 형식이 있으면 보내기 전에 막는다(7.6.2절). 실거래가 탭은 공공데이터포털에서 자료를 받기만 하고 국외로 보내는 자료가 없다(2026-11-19 보탬).

### 10.3 주민등록번호 가리기

- 주민등록번호는 법령에서 구체적으로 요구하거나 허용하는 경우가 아니면 처리할 수 없다(개인정보 보호법 제24조의2, [시행 2026. 9. 11.] 법률 제21445호, 2026-11-16 원문 확인). 이 도구는 업무 참고용이므로 주민등록번호를 저장하지 않고, 처리할 법령 근거를 주장하지 않는다.
- 계약서·등기부 사진은 올리기 전에 브라우저에서 사용자가 상자를 그어 가린다. 가린 부분은 원본 픽셀이 남지 않게 단색으로 덮고, 다시 인코딩해 EXIF·GPS를 지운다.
- 글자로 된 입력(메모 등)에 주민등록번호 형식(6자리-7자리)이 들어오면 저장 전에 경고하고 가리도록 한다.
- AI 결과에 주민등록번호 형식 문자열이 나오면 화면에 표시하지 않고 가린다.
- comibot은 고객 글을 가린 뒤 보내지만, 사진·녹음은 보내기 전에 글자로 가릴 수 없다(comibot 조사 결과). 사진은 사람이 가리는 방식밖에 없고, 녹음은 가릴 수 없다는 점을 10.4절에서 다룬다.

### 10.4 녹음 처리(통화·대면 상담)

- 통화는 운영자가 통화 당사자로서 직접 녹음한 파일만, 대면 상담은 운영자가 대화에 참여한 상태에서 화면 안 녹음으로 받은 음성만 다룬다. 제3자 대화 녹음이나 몰래 녹음 기능은 만들지 않는다(통신비밀보호법, **추가 확인 필요**: 법률 판단 아님).
- 대면 상담 화면 안 녹음은 녹음을 시작할 때 "손님께 안내하셨나요?" 안내를 한 번 띄운다(녹음·글자 정리·원본 1년 보관·국외 AI 전송 사실, 7.5.3절). 확인을 누르지 않아도 녹음된다(**확정**, DEC-WT-16, 2026-11-17 14:02:11 운영자 원문 "널널안 적용". 13:55:29에는 "법률 확인 전까지 '손님에게 안내함'을 눌러야 녹음이 켜짐"으로 정했다가 바꿈. 대장이 14:01:24에 추천한 "중간안"(손님마다 처음 한 번만 확인)은 고르지 않음). 대화 당사자 녹음은 합법이라는 판단은 대장 판단이고 변호사 확인은 아니다.
- 녹음에는 상대방의 목소리·대화 내용·개인정보가 들어 있고 가릴 수 없다. AI로 보내기 전에 "상대방 개인정보가 국외 AI 업체로 전송됩니다" 확인 단계를 둔다.
- 녹음 원본(통화 녹음 파일·화면 안 대면 녹음)은 기본 1년 보관한다. 사용자가 언제든 직접 지울 수 있고, 올린 날에서 1년이 지나면 정리 안내에 나온다. 자동으로 지우지 않는다(**확정**, DEC-WT-10, 2026-11-17 14:02:11 운영자 원문 "널널안 적용". 13:55:29에는 "기본 보관 안 함(메모 저장 뒤 삭제), 고른 경우만 30일"로 정했다가 바꿈). 변환이 실패하거나 `unknown`이어도 원본이 남아 있으므로 다시 실행할 수 있다. 올리다 끊겨 완성되지 않은 업로드 조각을 치우는 48시간 정리는 녹음 보관이 아니라 기술 정리다(**설계 선택**, 설계서 8.7·14.6절).
- 녹음 요약을 손님 메모로 저장할 때도 주민등록번호 형식 검사(10.3절)를 적용한다.
- 마이크는 녹음 화면 경로에서만 허용한다. 공개 화면과 다른 관리자 화면은 지금처럼 `Permissions-Policy: microphone=()`로 막는다(7.5.3절, DEC-WT-14).

### 10.5 서류 보존 의무

- 공인중개사법의 보존 기간(2026-11-16 원문 확인, 설계서 11.4절): 거래계약서 5년(법 제26조①, 시행령 제22조②), 중개대상물 확인·설명서 3년(법 제25조③, 시행령 제21조④), 전속중개계약서 3년(법 제23조②, 시행규칙 제14조②). "원본, 사본 또는 전자문서"로 보존할 수 있고, 공인전자문서센터에 보관하면 보존 의무가 없다.
- 결정(**확정**, DEC-WT-08 A안, 2026-11-17 13:55:29 운영자 원문 "A·B·C 적용, 결정 대기 추천대로", 14:02:11 "널널안 적용"에서도 그대로): 이 도구는 법정 보존의 공식 수단이 아니다. 공식 보존은 기존 방식(원본 서류철, 부동산거래계약시스템·공인전자문서센터 등)을 유지한다. 이 도구의 계약서는 주민등록번호를 가린 업무 참고용 사본이다. 주민등록번호는 저장하지 않는다(ADR-011 8번 그대로). 가린 사본이 법정 보존 "사본"으로 인정되는지는 판단하지 않는다.
- 이 도구의 보유기간·파기 기준(**확정**, DEC-WT-04, 2026-11-17 14:02:11 운영자 원문 "널널안 적용". 13:55:29에는 설계서 제안값(완료 거래 5년, 상담만 1년, 취소 거래 1년, 감사 로그 1년)으로 정했다가 바꿈): 손님 기록(손님·거래·메모·메모 창고·업무용 사본·사진)은 **사용자가 직접 지울 때까지 보관**한다. 기간을 두지 않고 자동으로 지우지 않는다. 거래계약서 등 법정 보존 대상은 법정 기간 이상 보존해야 하며, 공식 보존은 기존 방식이 맡는다(DEC-WT-08).
- 정리 안내(**설계 선택**): 기준일(손님은 마지막 연락일, 거래는 완료·취소일, 메모·사진·녹음은 올린 날)에서 1년이 지난 자료를 업무 도구 첫 화면에 "정리 안내 N건"으로 보여 준다. 사용자는 "지우기" 또는 "계속 보관"을 고르고, "계속 보관"을 누르면 1년 뒤 다시 안내한다(공개 매물 재확인 정책과 같은 방식). 설계서의 "파기 예정 N건" 안내와 `retention_until`은 이 "정리 안내 기준일"의 뜻으로 읽는다(설계서 8.7절).
- 자동 삭제는 손님 자료가 아닌 것만 한다: 감사 로그 3년(손님 개인정보 없음), AI 작업 기록(결과 초안) 확정·취소 후 30일(13:55:29 설계서 제안값 그대로). 운영자 PC 백업은 최근 3개만 둔다(13:55:29 설계서 제안값 그대로). 녹음 원본은 손님 자료처럼 자동 삭제하지 않는다(10.4절, DEC-WT-10).

### 10.6 처리방침 수정

- 지금 처리방침(`src/pages/privacy.astro`)은 홈페이지 방문자 정보(Cloudflare Web Analytics, Google 태그)만 다룬다. 6절에 "개인정보를 처리하는 기능을 추가할 경우 수집 목적·항목·보유기간을 먼저 정하고 이 방침을 수정한 뒤 적용합니다"라고 약속하고 있다.
- 단계 2 운영 시작 전에 추가할 항목(초안은 설계서 또는 별도 문서):
  - 처리 목적: 중개 업무 수행(상담 기록, 계약 일정 관리, 계약 관련 자료 보관)
  - 처리 항목: 10.1절 표
  - 보유기간·파기: 손님 기록은 사용자가 직접 지울 때까지 보관하고 1년마다 정리 안내, 감사 로그 3년, AI 작업 기록(결과 초안) 확정·취소 후 30일(DEC-WT-04, 10.5절). 백업에 남는 기간 포함(D1 Time Travel 7일 또는 30일, 운영자 PC 월간 백업 파일 최근 3개)
  - 녹음 원본 보관(단계 4): 통화 녹음 파일·화면 안 대면 녹음 원본을 기본 1년 보관하고, 사용자가 언제든 지울 수 있으며, 1년이 지나면 정리 안내(DEC-WT-10, 10.4절)
  - 처리위탁·국외 이전: Cloudflare(단계 2), OpenAI(단계 4). OpenAI 항목에는 대면·통화 녹음을 OpenAI(미국)로 보내 받아쓰기하는 국외 이전을 넣는다(DEC-WT-16, 10.2절)
  - 접근 범위: 손님 자료에 접근하는 관리자 계정이 2개라는 점과 작업 기록(감사 로그)을 남긴다는 점(5.3절)

- 처리방침 변경은 공개 화면 변경이므로 기존 공개 검수 절차(로컬 화면·PR CI 확인)를 따른다.

### 10.8 공공데이터 이용 조건 (단계 P, 2026-11-19 보탬)

### 10.9 중개대상물 표시·광고 명시사항 (단계 P, 2026-11-19 보탬)

법률 판단이 아니라 개발 요구사항이다. 2026-11-18 국가법령정보센터 원문 기준이며 구현 시점에 다시 확인한다.

- 공인중개사법 제18조의2와 시행령 제17조의2: 모든 표시·광고에 중개사무소 명칭·소재지·연락처·등록번호와 개업공인중개사 성명을 적고, 중개보조원에 관한 사항은 적지 않는다. 인터넷 표시·광고에는 매물의 소재지·면적·가격·종류·거래 형태와 건축물의 총 층수·사용승인일, 방향·방 개수·욕실 개수·입주 가능일·주차 대수·관리비를 더 적는다.
- 국토교통부 고시 「중개대상물의 표시·광고 명시사항 세부기준」(제2024-748호): 아파트 소재지는 지번·동·층수로 적되 의뢰인이 원하지 않으면 층수를 저·중·고로 적을 수 있다. 호수는 요구하지 않는다. 블로그를 따로 적은 조항은 없지만 빼는 조항도 없어, 블로그 글도 인터넷 표시·광고로 보고 보수적으로 적용한다(**추정**).
- 국토교통부 고시 「부당한 중개대상물 표시·광고행위의 유형 및 기준」(제2026-345호): 이미 계약된 줄 알면서 하는 광고, 가격·면적을 다르게 적는 광고, 교통시설 거리를 도보가 아닌 직선거리로 적는 광고 등을 부당 광고 예시로 든다.
- 제재(법 제51조, 시행령 별표 2 개별기준): 명시사항 위반은 과태료 50만 원, 부당한 표시·광고는 유형에 따라 250만 ~ 500만 원이다.
- 지어낸 손님 후기는 공정거래위원회 추천·보증 심사지침의 부당 광고 예시이고, AI로 만든 가상 인물은 표시가 필요하다. 이 도구는 후기와 가상 인물을 만들지 않는다.

- 하루 생성 요청 한도 40회(설계서 14.9절)를 모두 계약서 두 번 읽기에 쓴다고 해도 이론상 월 약 800달러까지 쓸 수 있다(하루 20건 × (Sol 0.222 + Astra 1.11달러) × 30일). 실제 보호선은 OpenAI 프로젝트의 월 예산 상한(DEC-WT-06)과 앱의 월 예상 비용 상한이다.

월 비용 범위(추정, 1달러 = 1,400원, 가정은 변경 전과 같고 단가만 바꿈):

| 기능 | 가정 | 모델 | 출력을 상한까지 다 쓸 때 | 출력이 평균 5,000토큰일 때 |
|---|---|---|---:|---:|
| 계약서 인식 | 월 20건, 건당 사진 3장(장당 입력 3,000토큰 가정) + 지시 2,000토큰, 두 번 읽기 | Sol 1회 + Astra 1회 | 약 26.6달러 | 약 8.6달러 |
| 녹음 요약 | 월 40건(합계 약 1,000분), 건당 글자 입력 8,000토큰 가정 | Sol | 약 8.6달러 | 약 2.6달러 |
| 등기부 인식 | 월 20건, 건당 입력 6,000토큰 가정 | Sol | 약 4.2달러 | 약 1.2달러 |
| 사진 글자·제목 | 월 200장, 장당 입력 3,000토큰, 출력은 상한 대신 5,000·2,000토큰 가정 | Sol | 약 11.2달러 | 약 5.2달러 |
| 녹음 → 글자 | 월 1,000분 × 분당 0.0045달러 | `gpt-transcribe` | 약 4.5달러 | 약 4.5달러 |
| 합계 | | | 약 55달러(약 7.7만 원) | 약 22달러(약 3.1만 원) |

- 참고(변경 전): 모든 작업을 `gpt-6-astra`로 했을 때는 같은 가정에서 음성 변환을 빼고 약 165달러(약 23만 원) ~ 약 60달러(약 8만 원)였다.
- 참고(계약서 교차의 비용): 계약서를 `gpt-6.1-sol` 두 번으로 읽으면 계약서 줄이 약 8.9달러 ~ 약 2.9달러로 줄어, 교차가 월 약 6 ~ 18달러를 더 쓴다. 이 차이와 정확도 차이를 단계 4 시작 때 함께 보고한다(테스트 체크리스트 T4-50a·T4-50b).
- 단계 P의 AI 블로그 글 초안(7.6.2, 2026-11-19 보탬)은 위 합계에 넣지 않았다. 월 30편, 편당 입력 약 4,000토큰 가정에서 출력을 상한까지 다 쓰면 약 6.2달러(약 8,700원), 평균 5,000토큰이면 약 1.7달러(약 2,400원)를 더한다.
- 이 범위는 가정에 따라 크게 달라진다. 특히 최고 추론 수준에서 실제로 쓰는 추론 토큰 수를 아직 모른다. 단계 4 첫 시험(가상 표본) 뒤 실제 토큰 수로 이 표를 다시 계산한다.
- 위 상한 가정에서도 AI 비용은 중개날개 비즈니스 등급(월 88,000원)보다 낮을 것으로 보인다(추정). 실제 토큰 수로 다시 계산한 결과를 단계 4 착수 승인 때 보고한다.

| 기능 | 월 비용 계산식 | 비고 |
|---|---|---|
| 계약서 인식 | 월 횟수 × 사진 장수 × 2(두 번 읽기) × (사진 입력 토큰 + 추론·출력 토큰) × 단가 | 고해상도 사진은 입력 토큰이 커짐 |

- 비용 통제: OpenAI 프로젝트 월 예산 상한(결정 대기 6) + Worker의 하루 호출 횟수 상한(설계서) + 화면의 이번 달 사용량 표시.
- 판단 기준: 구현 직전에 공식 단가로 위 식을 채워 월 예상 비용을 계산하고, 중개날개 구독료(월 88,000원)와 비교해 운영자에게 보고한다.

## 14. 단계별 일정 추정

**모두 추정이다.** 작업 시간은 작업 세션이 설계·구현·시험하는 시간이고, 운영자의 승인·실기기 확인·실제 사용 기간은 따로 적었다.
