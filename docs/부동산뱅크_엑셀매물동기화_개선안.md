# 부동산뱅크 엑셀 매물 동기화 및 수동 등록 개선안

> 목적: 부동산뱅크 중개회원 관리자에서 엑셀출력한 매물은 관리자 페이지에서 한 번에 가져오고, 그 밖의 네이버 매물은 같은 관리자 페이지에서 수동으로 등록·수정·종료한다.
>
> 두 입력 방식은 모두 현재 공개 매물과 같은 NaverListing 형식으로 저장한다. 홈페이지 카드 모양, 필터·정렬, 카드 클릭 시 네이버페이 부동산 개별 매물로 이동하는 동작은 바꾸지 않는다.
>
> 이 문서는 2026-08-26 실제 부동산뱅크 파일 전체 _2026-08-26.xls과 현재 저장소 코드를 기준으로 작성했다.

| 항목 | 결정 |
|---|---|
| 자동 가져오기 | 부동산뱅크 엑셀만 지원 |
| 기타 엑셀 | 한방광고.xls 등은 자동 파싱하지 않음 |
| 기타 매물 | 관리자 페이지에서 수동 등록 |
| 저장 데이터 | src/data/naver-listings.json |
| 공개 화면 | 기존 NaverListingCard와 NaverListingPager 그대로 사용 |
| 공개 링크 | https://fin.land.naver.com/articles/{네이버매물번호} |
| 원본 엑셀 | 브라우저에서만 읽고 서버·GitHub에 저장하지 않음 |
| 저장 방식 | 정제된 공개 JSON만 기존 관리자 Content API로 저장 |
| 크롤링 | 네이버·부동산뱅크·한방 크롤링은 이번 범위에서 제외 |
| 사진 | 이번 범위에서 제외 |

---

# 1. 최종 결정

이번 개선의 운영 원칙은 다음과 같다.

1. 부동산뱅크에 등록된 매물은 부동산뱅크 엑셀 파일로 일괄 반영한다.
2. 부동산뱅크에 없는 네이버 매물은 관리자 페이지에서 한 건씩 직접 등록한다.
3. 두 경로에서 생성한 매물은 모두 현재 NaverListing 형식으로 합쳐서 저장한다.
4. 부동산뱅크 엑셀에 없는 기존 매물은 자동 삭제하지 않는다.
5. 수동 매물의 종료는 관리자 화면에서 운영자가 명시적으로 처리한다.
6. 홈페이지에는 지금과 같은 카드가 나오며 카드 클릭 시 네이버 개별 매물로 이동한다.

즉, 한방광고.xls 등 공급처마다 서로 다른 엑셀 파서를 계속 추가하지 않는다.

~~~text
부동산뱅크 매물
  → 부동산뱅크 엑셀 가져오기
  → 공개 데이터 변환
  ┐
  ├→ 같은 naver-listings.json
  ┘
그 밖의 네이버 매물
  → 관리자에서 수동 등록
~~~

네이버 부동산 크롤링은 로그인·차단·화면/API 변경에 취약하고, 사이트가 원본 데이터를 통제하기 어렵다. 현재 규모에서는 부동산뱅크만 정형 가져오기를 지원하고 나머지를 수동으로 관리하는 편이 더 단순하고 안정적이다.

---

# 2. 변경하지 않는 사용자 화면

공개 페이지의 동작은 현재와 같아야 한다.

~~~text
홈페이지 매물 카드
  → 매물 종류·거래 유형·가격·면적·층·방향·설명 표시
  → 카드 클릭
  → https://fin.land.naver.com/articles/{id}
~~~

구현 시 다음 항목은 그대로 유지한다.

- NaverListingCard의 표시 구조
- NaverListingPager의 페이지 이동
- 기존 필터와 정렬
- 기본순을 선택했을 때 원래 순서와 1페이지 복원
- source 값 네이버페이 부동산
- fin.land.naver.com 개별 매물 링크
- 공개 사진이 없는 현재 카드 구조

부동산뱅크 가져오기와 수동 등록은 공개 UI를 새로 만드는 작업이 아니라, 현재 공개 UI에 들어갈 데이터를 관리하는 관리자 기능이다.

# 3. 현재 코드 기준 공개 데이터 형식

현재 src/lib/naver-listings.ts의 형식을 그대로 사용한다.

~~~ts
export type NaverListingTradeType =
  | "sale"
  | "jeonse"
  | "monthly-rent";

export interface NaverListing {
  id: string;
  title: string;
  propertyType: string;
  tradeType: NaverListingTradeType;
  priceLabel: string;
  areaLabel: string | null;
  floorLabel: string | null;
  direction: string | null;
  summary: string;
  confirmedAt: string;
  source: "네이버페이 부동산";
  url: string;
}
~~~

파일 전체 구조:

~~~json
{
  "checkedAt": "2026-08-26",
  "items": []
}
~~~

현재 scripts/content-validation.mjs의 검증도 유지한다.

- id는 숫자로만 된 네이버 매물번호
- id 중복 금지
- tradeType은 sale, jeonse, monthly-rent 중 하나
- title, propertyType, priceLabel, summary는 빈 문자열 금지
- areaLabel, floorLabel, direction은 문자열 또는 null
- confirmedAt은 YYYY-MM-DD
- source는 네이버페이 부동산으로 고정
- url은 해당 id의 https://fin.land.naver.com/articles/{id}

## 3.1 두 입력 방식의 책임

| 필드 | 부동산뱅크 엑셀 | 관리자 수동 등록 |
|---|---|---|
| id | 네이버번호에서 추출 | 운영자가 네이버 매물번호 입력 |
| title | 안전한 매물명·동 정보로 생성 | 운영자가 공개 제목 입력 |
| propertyType | 엑셀 매물종류 | 운영자가 선택 또는 입력 |
| tradeType | 매매·전세 매핑 | 운영자가 선택 |
| priceLabel | 만원 값을 현재 표시 형식으로 변환 | 네이버 공개 가격 표시를 입력 |
| areaLabel | 면적 컬럼 변환 | 네이버 공개 면적 표시를 입력 |
| floorLabel | 기존 ID 보존, 신규는 null | 공개된 층 정보만 선택 입력 |
| direction | 방향 컬럼 | 공개된 방향만 선택 입력 |
| summary | 특징을 안전 검사 후 사용 | 공개 설명을 직접 입력 |
| confirmedAt | 등록기간 시작일 후보 | 운영자가 확인일 입력 |
| source | 고정값 | 고정값, 입력 불가 |
| url | id로 자동 생성 | id로 자동 생성, 입력 불가 |

저장 형식에는 bank, hanbang 같은 출처 구분 필드를 새로 추가하지 않는다. 현재 스키마를 유지하고 네이버 매물번호를 공통 키로 사용한다.

# 4. 실제 부동산뱅크 파일 확인 결과

제공된 전체 _2026-08-26.xls 확인 결과:

- 매물 행: 42건
- 컬럼: 25개
- 모든 행에 부동산뱅크 매물번호와 네이버 매물번호가 함께 존재
- 거래 유형 샘플: 매매, 전세
- 매물 종류 샘플: 아파트, 아파트분양권, 단독/다가구
- 진행 상태 샘플: 서비스중, 서비스중 (전자홍보확인서)

확장자는 .xls지만 실제 내용은 EUC-KR HTML table이다.

~~~html
<meta
  http-equiv="Content-Type"
  content="application/vnd.ms-excel; charset=euc-kr">
<table>...</table>
~~~

1차 파싱 흐름:

~~~text
File
  → ArrayBuffer
  → TextDecoder("euc-kr")
  → DOMParser("text/html")
  → table, tr, td의 textContent만 추출
~~~

보안 원칙:

- 원본 HTML을 innerHTML로 화면에 넣지 않는다.
- 현재 부동산뱅크 HTML-table .xls만 허용한다.
- 바이너리 XLS나 XLSX를 잘못 추측해 읽지 않는다.
- 형식이 바뀌면 지원하지 않는 파일 형식으로 중단한다.
- 원본 행 전체를 콘솔이나 오류 메시지에 출력하지 않는다.

# 5. 개인정보와 공개 금지 정보

실제 부동산뱅크 파일에는 공개 데이터와 개인정보·내부정보가 섞여 있다.

다음 값은 결과 객체로 복사하지 않는다.

- 소유자명
- 소유자 핸드폰번호
- 매도자명
- 매도자 핸드폰번호
- 메모
- 상세설명
- 정확한 호수
- 내부 연락처

원본 파일은 다음 위치에 남기지 않는다.

- Worker
- GitHub
- Cloudflare 로그
- LocalStorage
- IndexedDB
- 분석 로그

## 5.1 매물설명

아파트·분양권의 매물설명에 다음처럼 동과 호가 함께 있으면:

~~~text
507동 2405호
~~~

공개 제목에는 다음만 사용한다.

~~~text
507동
~~~

2405호는 즉시 버린다. 변환 결과에 호수나 전화번호 패턴이 남으면 저장을 차단한다.

## 5.2 층 정보

부동산뱅크 엑셀의 해당층/총층을 신규 매물에 자동 공개하지 않는다.

- 같은 네이버 ID가 기존 데이터에 있으면 기존 floorLabel을 보존한다.
- 신규 엑셀 매물은 floorLabel을 null로 둔다.
- 운영자가 네이버에 실제 공개된 층 정보를 확인한 경우 수동 편집으로 입력할 수 있다.
- 정확한 층을 저·중·고로 임의 계산하지 않는다.

# 6. 부동산뱅크 엑셀 매핑

| 거래 | 사용 | tradeType | 매매→sale, 전세→jeonse |

| 메모 | 폐기 | - | 내부 메모 |
| 사진 개수 | 미사용 | - | 이미지 데이터가 아님 |

## 6.1 네이버 매물번호

실제 예:

~~~text
143367919  (  2645754923  )
~~~

의미:

~~~text
143367919  = 부동산뱅크 매물번호
2645754923 = 네이버 매물번호
~~~

공백 차이는 허용하되 두 숫자를 명확히 분리한다.

~~~regex
^\s*(\d+)\s*\(\s*(\d+)\s*\)\s*$
~~~

공개 데이터에는 네이버 번호만 저장한다.

~~~text
id  = 2645754923
url = https://fin.land.naver.com/articles/2645754923
~~~

네이버 번호가 없거나 중복이면 저장을 차단한다.

## 6.2 제목

아파트·분양권:

~~~text
리더스시티5BL + 507동 2405호
→ 리더스시티 5블록 507동
~~~

명확한 현재 표기만 정규화한다.

~~~text
리더스시티4BL → 리더스시티 4블록
리더스시티5BL → 리더스시티 5블록
~~~

신규 단독/다가구처럼 안전한 제목 생성 규칙이 확정되지 않은 행은 제목 확인 필요로 표시하고 자동 반영하지 않는다. 같은 ID의 기존 매물이 있으면 기존 제목을 보존할 수 있다.

## 6.3 거래와 가격

확인된 자동 매핑:

~~~text
매매 → sale
전세 → jeonse
~~~

가격 예:

~~~text
39000 → 3억 9,000
52000 → 5억 2,000
45780 → 4억 5,780
~~~

부동산뱅크 월세 행은 실제 샘플을 확인하지 못했으므로 자동 매핑하지 않는다.

~~~text
부동산뱅크 엑셀에서 월세 발견
→ 월세 엑셀 샘플 필요 표시
→ 전체 저장 차단
~~~

이는 부동산뱅크 자동 가져오기 제한이다. 관리자 수동 등록에서는 monthly-rent를 선택하고 네이버에 공개된 가격 표시를 직접 입력할 수 있다.

## 6.4 면적

예:

~~~text
81.32B/59.64
→ 81.32B㎡ · 전용 59.64㎡
~~~

현재 사이트의 표기와 일치하도록 실제 데이터의 면적 표기 규칙을 재사용한다. 파싱이 불확실하면 임의 보정하지 않고 확인 필요로 보낸다.

## 6.5 확인일

등록기간 시작일을 confirmedAt 후보로 사용하되, 구현 전에 현재 의미와 대조한다.

- YYYY-MM-DD로 정규화
- 전체 checkedAt보다 미래일 수 없음
- 파일명 날짜만 믿지 않고 실제 선택일 또는 파일 내 날짜와 비교

# 7. 엑셀 diff와 병합 정책

비교 키는 네이버 매물번호다.

| 분류 | 조건 | 동작 |
|---|---|---|
| 신규 | 엑셀에 있고 사이트에 없음 | 안전 검증 후 추가 후보 |
| 변경 | 같은 ID이고 공개 필드가 다름 | 변경 전·후 미리보기 |
| 동일 | 같은 ID이고 공개 필드가 같음 | 저장 변경 없음 |
| 사이트에만 존재 | 사이트에 있고 엑셀에 없음 | 유지, 자동 삭제 금지 |
| 확인 필요 | 파싱·보안·지원 상태 오류 | 저장 차단 |

## 7.1 사이트에만 존재하는 매물

사이트에만 존재하는 항목은 정상 상태일 수 있다.

- 부동산뱅크가 아닌 경로에서 수동 등록한 매물
- 엑셀 출력 필터에서 빠진 매물
- 부동산뱅크와 네이버 반영 시점이 다른 매물
- 일시적으로 출력되지 않은 매물

따라서 엑셀에 없다는 이유만으로 삭제·종료하지 않는다.

## 7.2 같은 ID가 있을 때

부동산뱅크 엑셀과 현재 사이트에 같은 네이버 ID가 있으면:

- title, propertyType, tradeType, priceLabel, areaLabel, direction, summary, confirmedAt은 diff를 보여준다.
- floorLabel은 기존값을 보존한다.
- source와 url은 고정 규칙으로 검증한다.
- 운영자가 미리보기를 승인한 뒤에만 갱신한다.

수동으로 입력한 매물이라도 나중에 부동산뱅크 엑셀에 같은 ID가 나타나면 같은 규칙을 적용한다. 별도 origin 필드가 없으므로 ID 기준의 일관된 병합을 사용한다.

## 7.3 순서

행 순서만 바뀌어 대규모 diff가 생기지 않게 한다. 기존 순서를 최대한 유지하고 신규 항목만 정해진 위치에 추가한다.

# 8. 관리자 화면 구성

구현 대상은 /admin/listings/editor/이다. 현재 코드에 해당 편집 화면이 없다면 새로 만들고, /admin/listings/의 현재 목록에서 이동할 수 있게 한다.

한 화면을 다음 두 구역으로 나눈다.

~~~text
네이버 매물 관리

[A. 부동산뱅크 엑셀 가져오기]

[B. 매물 직접 등록·수정]

[C. 현재 등록 매물 목록]
~~~

## 8.1 A. 부동산뱅크 엑셀 가져오기

안내:

~~~text
부동산뱅크 매물관리에서 엑셀출력한 파일만 선택해 주세요.
원본 파일은 서버로 전송하지 않습니다.
~~~

기능:

- .xls 파일 선택
- 파일 형식과 필수 컬럼 검사
- 전체·신규·변경·동일·사이트에만 존재·확인 필요 수 표시
- 개인정보 제거 결과 표시
- 변경 전·후 미리보기
- 오류가 없을 때만 변경사항 반영

표시 예:

~~~text
전체              42건
신규               2건
변경               3건
동일              37건
사이트에만 존재     8건
확인 필요           0건
~~~

보안 확인:

~~~text
✓ 소유자·매도자 정보 저장 안 함
✓ 전화번호 저장 안 함
✓ 정확한 호수 저장 안 함
✓ 내부 메모 저장 안 함
✓ 원본 파일 서버 전송 안 함
~~~

저장 정책:

- 오류가 한 건이라도 있으면 전체 저장 차단
- 안전한 행만 몰래 부분 저장하지 않음
- 저장 전 신규·변경 수를 다시 확인
- 사이트에만 존재하는 항목은 유지

## 8.2 B. 매물 직접 등록·수정

이 영역은 부동산뱅크 엑셀에 없는 네이버 매물을 위한 수동 입력 화면이다.

수동 등록 가능 조건:

- 네이버페이 부동산에 공개된 매물번호가 있음
- 공개 개별 매물 링크를 만들 수 있음
- 개인정보가 아닌 공개 정보만 입력함

네이버 번호가 없는 내부 매물은 현재 NaverListing 형식과 맞지 않으므로 이번 화면에 등록하지 않는다.

### 수동 등록 필드

| 화면 필드 | 필수 | 저장값 | 입력 규칙 |
|---|---:|---|---|
| 네이버 매물번호 | 예 | id | 숫자만 입력 |
| 매물 제목 | 예 | title | 예: 리더스시티 5블록 507동, 정확한 호수 금지 |
| 매물 종류 | 예 | propertyType | 기존 종류 선택 + 필요한 경우 직접 입력 |
| 거래 유형 | 예 | tradeType | 매매, 전세, 월세 선택 |
| 가격 표시 | 예 | priceLabel | 네이버에 공개된 표시 그대로 |
| 면적 표시 | 선택 | areaLabel | 예: 81B㎡ · 전용 59.64B㎡ |
| 층 표시 | 선택 | floorLabel | 네이버에 공개된 값만 입력 |
| 방향 | 선택 | direction | 공개된 방향만 입력 |
| 한줄 설명 | 예 | summary | 연락처·호수·소유자 정보 금지 |
| 확인일 | 예 | confirmedAt | YYYY-MM-DD |
| 출처 | 자동 | source | 네이버페이 부동산 고정 |
| 상세 주소 | 자동 | url | 네이버 매물번호로 생성 |

가격 표시는 현재 공개 카드가 사용하는 priceLabel과 같은 형식을 입력한다.

~~~text
매매·전세 예: 5억 2,000
매매·전세 예: 3억
월세 예: 네이버 개별 매물에 실제 표시된 보증금/월세 문자열
~~~

월세 문자열은 화면 예시만 보고 추측해서 생성하지 않는다. 실제 네이버 개별 매물에 공개된 표시를 운영자가 입력하고 카드 미리보기에서 확인한다.

### 자동 생성 필드

운영자는 source와 url을 직접 수정할 수 없다.

~~~text
source = 네이버페이 부동산
url    = https://fin.land.naver.com/articles/{id}
~~~

네이버 매물번호를 입력하면 다음을 바로 표시한다.

- 생성될 네이버 링크
- 중복 여부
- 현재 등록된 같은 ID 존재 여부
- 카드 미리보기

### 등록

새 ID:

~~~text
[카드 미리보기]
[등록]
~~~

같은 ID가 이미 있으면 신규 등록을 거부하고 편집 화면으로 안내한다.

### 수정

현재 등록 매물 목록의 수정 버튼을 누르면 해당 값을 폼에 불러온다.

- 네이버 ID 변경은 원칙적으로 금지
- 다른 ID로 바꿔야 하면 새 매물 등록 후 기존 매물 종료
- 저장 전에 변경 전·후 표시
- source와 url 고정

### 종료·삭제

수동 매물 또는 기존 매물의 종료는 명시적인 운영자 동작으로만 처리한다.

~~~text
[등록 종료]
→ 매물 제목과 네이버 번호 재확인
→ "홈페이지 목록에서 제거됩니다" 확인
→ 선택한 ID 한 건만 제거
~~~

- 엑셀 누락으로 자동 종료하지 않음
- 목록 전체 삭제 기능을 만들지 않음
- 취소 시 아무것도 저장하지 않음
- 현재 스키마에 종료 상태가 없으므로 1차에서는 items에서 제거

# 9. 수동 입력 개인정보 검증

수동 입력도 엑셀 가져오기와 같은 공개 안전 검사를 적용한다.

차단 후보:

- 휴대전화·전화번호 패턴
- 정확한 동·호 조합에서 호수 부분
- 소유자, 매도자, 임대인 등 개인 식별 문구
- 내부 메모성 문구
- HTML 태그 또는 스크립트
- fin.land.naver.com이 아닌 URL

검증 오류에는 실제 개인정보 값을 반복해서 노출하지 않는다.

~~~text
한줄 설명에 공개 금지 정보가 포함되어 저장할 수 없습니다.
~~~

층 정보는 네이버에 이미 공개된 값만 입력하라는 안내를 붙인다. 완전한 개인정보 판별을 정규식만으로 보장할 수 없으므로, 저장 전 카드 미리보기를 필수로 둔다.

# 10. 관리자 저장 API

새 원본 엑셀 업로드 API를 만들지 않는다.

현재 패턴:

~~~text
GET /api/admin/v1/content/{resource}
PUT /api/admin/v1/content/{resource}
~~~

naver-listings 리소스를 연결해 다음 흐름을 재사용한다.

- Cloudflare Access 인증
- Email OTP/JWT 검증
- CSRF 검증
- GitHub content SHA 충돌 검증
- content validation
- GitHub 저장
- 자동 배포

필요한 리소스 매핑 후보:

~~~js
"naver-listings": "src/data/naver-listings.json"
~~~

서버 경계를 넘는 값은 항상 정제된 공개 JSON이다.

~~~json
{
  "data": {
    "checkedAt": "2026-08-26",
    "items": [
      {
        "id": "2645402920",
        "title": "리더스시티 5블록 507동",
        "propertyType": "아파트",
        "tradeType": "sale",
        "priceLabel": "3억 9,000",
        "areaLabel": "81.32B㎡ · 전용 59.64㎡",
        "floorLabel": null,
        "direction": "남서향",
        "summary": "공개 가능한 매물 설명",
        "confirmedAt": "2026-08-26",
        "source": "네이버페이 부동산",
        "url": "https://fin.land.naver.com/articles/2645402920"
      }
    ]
  },
  "sha": "현재 콘텐츠 SHA"
}
~~~

엑셀 가져오기와 수동 등록 모두 브라우저에서 현재 items와 병합한 전체 정제 JSON을 같은 PUT API로 저장한다.

네이버 매물번호가 없어 공개 링크를 만들 수 없습니다.

공개 금지 정보가 감지되어 저장하지 않았습니다.
입력 내용을 확인해 주세요.
~~~

## 11.5 GitHub SHA 충돌

~~~text
다른 변경이 먼저 저장되었습니다.
최신 매물 목록을 다시 불러온 뒤 다시 시도해 주세요.
~~~

충돌이 나면 자동 덮어쓰지 않는다. 최신 데이터로 엑셀 diff를 다시 계산하거나 수동 편집 내용을 다시 적용한다.

~~~

- 현재 데이터 src/data/naver-listings.json을 샘플 엑셀로 바로 덮어쓰지 않는다.
- 테스트 fixture는 가상 개인정보만 사용한다.
- 실제 사용자 엑셀 파일을 Git에 추가하지 않는다.
- 현재 공개 스키마를 바꾸지 않는다.
- 공통 validation을 약화하지 않는다.

# 17. 운영 절차

## 17.1 부동산뱅크 매물

~~~text
1. 부동산뱅크에서 매물 등록·수정
2. 부동산뱅크의 기존 기능으로 네이버 전송
3. 부동산뱅크 매물관리에서 엑셀출력
4. 행복한부동산 관리자 → 네이버 매물 관리
5. 부동산뱅크 엑셀 파일 선택
6. 신규·변경·사이트에만 존재·오류 확인
7. 변경사항 반영
8. 배포 후 공개 카드와 네이버 링크 확인
~~~

부동산뱅크 매물은 홈페이지에 다시 한 건씩 입력하지 않는다.

## 17.2 그 밖의 네이버 매물

~~~text
1. 네이버 개별 매물에서 공개 정보와 매물번호 확인
2. 행복한부동산 관리자 → 네이버 매물 관리
3. 매물 직접 등록 선택
4. 공개 정보만 입력
5. 자동 생성된 네이버 링크 확인
6. 카드 미리보기 확인
7. 등록
8. 배포 후 공개 카드 클릭 확인
~~~

가격 변경 등은 해당 매물의 수정 버튼으로 처리한다. 광고가 끝나면 등록 종료 버튼으로 선택한 매물만 제거한다.

# 18. 구현용 요약 프롬프트

~~~text
현재 저장소의 CODEX.md와 AGENTS.md를 먼저 읽고 실제 코드 기준으로 작업하라.

목표:
1. /admin/listings/editor/에 네이버 매물 관리 화면을 만든다.
2. 자동 파일 가져오기는 부동산뱅크 EUC-KR HTML-table .xls만 지원한다.
3. 한방광고.xls와 다른 공급처 파일 파서는 만들지 않는다.
4. 부동산뱅크가 아닌 네이버 매물은 같은 화면에서 수동 등록·수정·종료한다.
5. 두 입력 경로 모두 현재 NaverListing 스키마로 src/data/naver-listings.json에 저장한다.
6. 공개 카드와 fin.land.naver.com/articles/{id} 클릭 동작은 유지한다.

필수 보안:
- 원본 XLS를 서버·GitHub·로그·브라우저 저장소에 남기지 않는다.
- 소유자·매도자·전화번호·정확한 호수·상세설명·메모를 결과에 넣지 않는다.
- 원본 HTML은 textContent만 읽고 innerHTML로 삽입하지 않는다.
- 수동 title과 summary에도 개인정보 검사를 적용한다.
- source는 네이버페이 부동산으로 고정한다.
- url은 숫자 id로 자동 생성하며 직접 수정하게 하지 않는다.

병합:
- 네이버 매물번호를 키로 사용한다.
- 신규·변경·동일·사이트에만 존재·확인 필요를 표시한다.
- 엑셀에 없는 기존 항목과 수동 등록 항목을 자동 삭제하지 않는다.
- 같은 ID의 기존 floorLabel은 보존하고 신규 엑셀 항목은 null로 둔다.
- 오류가 있으면 부분 저장하지 않는다.
- 저장 전 변경 미리보기와 카드 미리보기를 제공한다.

수동 폼:
- 네이버 매물번호
- 제목
- 매물 종류
- 거래 유형
- 가격 표시
- 면적 표시
- 층 표시
- 방향
- 한줄 설명
- 확인일
- source와 url은 자동
- 중복 ID는 편집으로 안내
- 종료는 명시적 확인 후 선택한 한 건만 제거

저장:
- 기존 Admin Content API, Cloudflare Access, CSRF, SHA 충돌, GitHub 저장을 재사용한다.
- raw XLS 업로드 API를 만들지 않는다.
- worker의 naver-listings 리소스 매핑과 validation을 연결한다.
- 현재 공개 스키마와 기존 검증을 약화하지 않는다.

부동산뱅크 월세:
- 실제 월세 엑셀 샘플 없이 자동 매핑을 추정하지 않는다.
- 엑셀 월세 행은 오류로 저장을 막는다.
- 수동 등록에서는 monthly-rent를 허용하고 네이버 공개 가격 표시를 직접 입력한다.

검증:
- 가상 fixture만 사용한다.
- npm test, npm run check, npm run build, Wrangler dry-run을 확인한다.
- 브라우저에서 엑셀 분석, 수동 등록, 수정, 종료, 공개 카드 클릭을 검수한다.
- 사용자 요청 밖 리팩터링과 DB/CMS 도입은 하지 않는다.
~~~

# 19. 최종 운영 모습

~~~text
부동산뱅크 등록 매물
  → 엑셀출력
  → 관리자에서 일괄 가져오기
                         ┐
                         ├→ 현재와 같은 홈페이지 매물 카드
                         └→ 클릭 시 네이버 개별 매물
그 밖의 네이버 매물
  → 관리자에서 직접 등록
~~~

이 구조의 목표는 공급처마다 새 크롤러나 엑셀 파서를 늘리는 것이 아니다.

- 자주 사용하는 부동산뱅크 매물은 일괄 반영한다.
- 나머지는 현재 공개 포맷에 맞춰 관리자가 직접 관리한다.
- 모든 매물은 같은 카드와 같은 네이버 링크로 사용자에게 보인다.
- 수동 매물은 부동산뱅크 엑셀에 없더라도 안전하게 유지된다.
